先在脑中搭起一张图：RAG 不是“把文档塞给模型”。

RAG 的中文意思可以先理解为“先找资料，再让模型基于资料回答”。产品经理要判断的不是向量库名字，而是资料是否可信、候选是否找全、引用是否能回放、旧知识是否会被误用。

先讲资料动作，再讲术语

每个英文词都先回答“它在知识链路里帮谁做什么判断”。

用错误答案划边界

不把“接了知识库”当完成，而是指出第一个会导致错答的节点。

带着开放资料做方案

可以回看解释和示例，目标是写出可验证的 RAG 产品方案。

资料源答案依据在哪里

负责限定哪些文档可信、适用、可被引用。

→
切片索引资料怎样被找

负责把长资料切成小段并转成可检索的表示。

→
召回重排候选怎样进入上下文

负责找候选、过滤、排序，并把证据放到模型前面。

→
引用更新答案怎样发布和维护

负责标出处、限制结论、处理过期和失败。

定位资料切成小段找候选排证据记录更新

知识库的第一步，是不是把所有文档都倒进去？

先别急着建库。资料源是答案的地基：哪些文档可信、适用、可引用、可给当前用户看，必须先被产品定义。

0 / 2 步

Source

就是答案可以依赖的资料来源

它可能是制度、FAQ、合同、课程笔记或产品手册。

能决定：答案依据范围不能决定：模型是否理解正确

Permission

就是谁能看哪份资料

同一知识库里可能有公开文档、内部文档和个人记录。

能限制：资料可见性不能替代：答案引用校验

Scope

就是资料适用于哪个问题

旧版本、外地区制度、非目标产品资料都可能相似但不适用。

能帮助：过滤候选不能证明：没有搜到就不存在
白话解释

资料源像图书馆的准入名单：不是书越多越好，而是先确定哪些书能被这次回答使用。

它不等于什么

把公司网盘全量导入不等于知识更完整。权限、版本和适用范围没定义，召回越多越容易错。

看起来完整，但错误全量文档 → 直接建向量库

用户可能召回没有权限看的资料，或命中过期制度。

正确的产品链路问题类型 → 可信资料源 → 权限范围 → 版本范围 → 可引用字段

先定义资料准入，再让检索系统找候选。

完整示范：HR 政策助手先管资料准入

现象：员工问病假规则，系统召回了外包员工手册。

  1. 已知事实文本相似，但身份和适用范围不同。
  2. 第一个错误节点没有在资料源层写清员工类型和版本边界。
  3. 正确动作按身份、地区、版本过滤资料，再进入切片和检索。
  4. 保持不变任何 RAG 方案都先定义可用资料，再谈召回效果。
理解检查：全量导入前第一步是什么

团队要做客服知识库，准备把网盘里的所有文档先导进去。第一步应该做什么？

留下一个理解或疑问

切片为什么会让答案变好，也会让答案断章取义？

切片就是把长资料切成模型和检索系统能处理的小段。切得太大，候选里噪音多；切得太小，关键上下文会断掉。

0 / 2 步
白话解释

切片像把一本手册贴标签分柜。问题不是每段多少字最先进，而是用户问问题时能不能找回完整的判断依据。

它不等于什么

固定 500 字一刀切不等于标准方案。制度条款、FAQ、代码注释和课程章节需要不同边界。

看起来规整，但错误每 500 字切一段 → 直接入库

可能把条件、例外和结论切开，答案只看到一半。

正确的产品链路问题形态 → 自然段落 → overlap → 元数据 → 示例回放

围绕真实问题检查切片能否带回完整证据。

完整示范：报销政策被切断先保留条件和例外

现象：助手回答“培训费可报销”，但被切掉的下一段写着“仅限审批通过课程”。

  1. 已知事实结论和限制条件被拆进不同切片。
  2. 第一个错误节点切片边界破坏了业务判断单元。
  3. 正确动作按条款或问答单元切片，并保留标题、版本和相邻上下文。
  4. 保持不变切片要围绕可回答问题的最小完整证据，而不是固定字数。
理解检查：条款被切断时先改什么

答案频繁漏掉“例外条件”，你发现例外条件总在相邻切片里。第一步应该怎么改？

一个功能手册包含入口、权限、步骤、失败提示和常见问题。请设计切片边界、需要带的元数据和一次回放检查。

需要提示时展开

思考“用户问一个问题时，哪几段必须一起出现才不会误导”。

方案已记录。

按“一个可执行任务”切片，例如入口+权限+步骤+失败提示作为主片，FAQ 单独成片并带功能名、版本、角色、更新时间。用真实问题回放，检查是否能同时召回步骤和限制条件。

留下一个理解或疑问

向量索引找到了“相似”，为什么还可能没有找到答案？

向量化是把文本变成可比较的位置，索引是让系统快速找相近片段。相近只是候选，不等于覆盖了问题所需事实。

0 / 2 步
白话解释

向量索引像按意思找资料的地图。它能找到像这个问题的片段，但不知道这些片段是否最新、是否完整、是否有权限。

它不等于什么

相似度分数不是准确率。召回第一名也可能只是问法相似，不包含可发布答案。

看起来科学，但错误similarity = 0.91 → 直接回答

高相似度只说明语义近，不能证明答案完整或适用。

正确的产品链路召回候选 → 看覆盖 → 查元数据 → 不足则二次检索或拒答

把向量检索当找候选，不当最终裁判。

完整示范：只召回定义，没有召回步骤先看覆盖缺口

现象：用户问“如何申请退款”，系统召回了退款定义，却没有召回操作步骤。

  1. 已知事实候选相似，但只覆盖概念，不覆盖流程。
  2. 第一个错误节点把相似片段当成完整答案。
  3. 正确动作按意图补充关键词或结构化过滤，召回流程类资料。
  4. 保持不变检索结果要覆盖用户任务，不只是语义相似。
理解检查：高相似但不覆盖任务怎么办

用户问操作步骤，召回第一名是概念定义，分数很高。第一步应该怎么处理？

带着资料做一次：售后助手召回策略

售后问题包括“是什么”“怎么做”“能不能退”“异常怎么办”。请设计索引字段和召回后覆盖检查。

需要提示时展开

除了正文向量，想想业务类型、产品线、角色、版本、问题意图这些元数据。

方案已记录。

正文向量配合产品线、问题意图、版本、角色和资料类型元数据；召回后检查是否覆盖操作步骤、限制条件和异常处理。只命中定义时触发二次检索或回答“当前资料不足以给出步骤”。

留下一个理解或疑问

检索参数是不是越大越好？

top_k、阈值和过滤条件会同时影响召回、噪音、延迟和成本。产品经理要知道调参解决什么问题，也要知道它解决不了资料缺失。

0 / 2 步
白话解释

检索像从资料库拿候选卡片。拿太少可能漏证据，拿太多会把无关内容塞给模型。

它不等于什么

把 top_k 调大不等于更准确。如果资料源错、切片断、权限缺，拿更多只会放大问题。

看起来稳妥，但错误答错 → top_k 加到 50

模型会收到更多噪音，延迟和成本上升，引用也更难核对。

正确的产品链路看错因 → 调过滤/阈值/top_k → 回放样例 → 记录成本

每次调参都要绑定具体错误类型和评测样例。

完整示范：跨产品线误召回先加过滤，不先加数量

现象：A 产品问题经常召回 B 产品文档，团队想增加候选数量。

  1. 已知事实错误来自产品线混入，不是候选数量不足。
  2. 第一个错误节点用更大的 top_k 解决过滤缺失。
  3. 正确动作先用产品线、版本和权限过滤，再调候选数量。
  4. 保持不变检索参数要服务错因，而不是凭感觉变大。
理解检查：跨产品线错答先改什么

A 产品问答混入 B 产品资料，答案错得很稳定。第一步应该怎么处理？

带着资料做一次：课程知识库检索参数

课程问答经常回答到上一周内容。请设计过滤条件、候选数量、失败时展示和一组回放样例。

需要提示时展开

先过滤课程周次、概念标签和正式状态权限，再决定召回数量。

方案已记录。

先按课程周次、概念标签、资料权限和版本过滤；top_k 从小候选集开始，用“本周概念、跨周相似词、旧版本规则、无资料问题”回放。检索不足时展示“当前资料不足”，不让模型凭记忆补齐。

留下一个理解或疑问

候选找到了，为什么还要重排、引用和限制答案？

重排是把多个候选按当前问题重新排序；引用是让答案能回到原文；限制答案是承认资料不足时不能硬答。

0 / 2 步
白话解释

召回像拿来一摞资料，重排像把最能回答问题的放到最上面，引用像把页码贴在答案旁边。

它不等于什么

有 citation 不等于 claim 被支持。引用位置要真的支撑答案里的那句话。

看起来可信，但错误答案后面挂 3 个链接 → 发布

链接可能只是主题相近，并没有支撑具体结论。

正确的产品链路候选重排 → claim 对齐 quote → 标出处 → 不足则限制结论

让每个关键结论都能回到可见证据。

完整示范：引用不能支撑结论先缩小 claim

现象：答案说“所有用户都可退款”，引用原文只写“会员用户可退款”。

  1. 已知事实引用存在，但支撑范围更窄。
  2. 第一个错误节点claim 超过 quote 能证明的范围。
  3. 正确动作缩小结论为会员用户，或标记普通用户规则未检索到。
  4. 保持不变引用不是装饰，答案范围必须小于等于证据范围。
理解检查：引用范围小于答案怎么办

引用只支持会员用户退款，答案却写成所有用户都可退款。第一步应该怎么处理？

带着资料做一次：招聘政策答案怎样引用

招聘助手回答“这个候选人是否符合岗位要求”。请说明哪些 claim 必须绑定原简历或岗位要求，哪些只能写 limitation。

需要提示时展开

候选人的经历、岗位硬条件、模型推断出的潜力，证据权限不同。

方案已记录。

硬条件结论绑定岗位要求和简历原文；经历摘要绑定简历逐字片段；潜力、文化匹配等无法从当前资料证明的内容只能写为待人工确认或不输出。每条关键 claim 都要能回放到 source 和 quote。

留下一个理解或疑问

知识更新是不是定时重建向量库就够了？

知识更新要处理新增、修改、删除、过期和回滚。重建索引只是技术动作，产品上还要知道用户何时会看到新知识，旧答案如何失效。

0 / 2 步
白话解释

知识库像货架。上新、下架、改价格、召回旧货都要有记录，否则模型可能拿旧货当新品卖。

它不等于什么

每天凌晨重建一次不等于知识可靠。删除的资料、紧急政策、失败索引和缓存答案都要处理。

看起来省心，但错误每天全量重建 → 默认最新

当天紧急更新可能仍被旧索引回答，删除资料也可能被缓存命中。

正确的产品链路变更事件 → 增量更新 → 版本标记 → 回放检查 → 旧答案失效

让知识生命周期能被观察和回滚。

完整示范：当天政策更新未生效先查版本和索引状态

现象：政策下午 3 点更新，助手晚上仍引用上午旧文档。

  1. 已知事实资料源已更新，但索引或缓存可能未更新。
  2. 第一个错误节点把文档系统更新当成检索系统已更新。
  3. 正确动作记录版本、触发增量索引、回放关键问题并让旧引用失效。
  4. 保持不变会变的知识要有版本、更新时间和失败可见性。
理解检查：资料已改但答案仍旧怎么办

政策文档已经更新，但 RAG 助手仍引用旧规则。第一步应该检查什么？

带着资料做一次：法务知识库更新策略

法务资料有紧急下架、每周更新和历史留档。请设计更新触发、版本显示、失败告警和旧答案处理。

需要提示时展开

把“新增、修改、删除、失败、回滚”分别写出来。

方案已记录。

新增和修改触发增量索引并写入版本；紧急下架立即标记不可召回并清理缓存；索引失败时暂停相关答案或转人工；保留历史版本用于审计，但默认回答只引用当前有效版本。

留下一个理解或疑问

综合工作坊：修好一个“接了知识库但仍然乱答”的产品方案。

这不是记忆测试。你可以回看任意模块、打开提示并修改方案。目标是把资料源、切片、索引、检索、重排、引用和更新连成一份可评审的 RAG 方案。

错误方案：把全部网盘文档导入向量库；按固定字数切片；召回 top_k=20 后直接塞给模型；答案挂三个链接但不校验 claim；知识每天重建一次，删除资料不处理缓存。

请改成：先限定资料源和权限，再设计切片、索引、检索过滤、重排引用、更新失效和降级边界。
工作坊路线：不知道从哪里开始时按这五步走
  1. 资料哪些来源可信、适用、可引用，谁能看？
