什么时候要调用工具：当任务需要执行动作时

工具调用适合执行明确动作，例如查询状态、写入记录、触发流程或拉取结构化数据。

0 / 2 步

查询状态

需要读数据

查任务进度、查询答辩记录、拉取历史反馈。

写入记录

需要改状态

保存追问、更新答辩结果或写入评价。

触发流程

需要调用系统

发起审批、提交记录或更新工作流状态。

白话解释

工具像给 Agent 一把扳手：它是去拧螺丝的，不是负责告诉你要不要装这颗螺丝。

它不等于什么

它不是更聪明的聊天，也不是把所有问题都自动化。

错误写法一切都交给模型，自然会知道何时调用接口

没有动作边界，模型容易把展示、判断和执行混在一起。

产品化写法明确哪些任务必须落到查询、写入或触发流程

动作清楚后，才知道是否需要工具。

完整示范：更新答辩记录是不是要调用工具先看动作，再看接口
  1. 已知事实用户完成了一轮答辩，需要把追问和结论写入记录。
  2. 工具可做如果系统有写入接口，就应该由工具保存。
  3. 工具不可做如果只是展示总结，未必需要调用写入动作。
  4. 产品动作先判断是否是“要改状态”的动作，再决定是否接工具。

工具调用不能补什么：先分动作失败，不要把它都怪到 Prompt 上

工具调用有接口、权限和状态边界。只要其中一层不成立，就不能把失败解释成“模型不够聪明”。

0 / 2 步
白话解释

工具调用解决的是动作落地，不是让模型自动知道权限、接口格式和状态后果。

它不等于什么

它不是万能执行器，也不是只要接上就会成功。

错误归因工具调用失败，继续让 Prompt 重试

如果接口不存在或没有权限，重试也不会改变结果。

正确归因先看动作、权限、接口和状态，再决定是否重试

先分类失败，再决定是改工具、补权限还是走人工。

完整示范：写入记录失败怎么办先找失败层，再改对应层
  1. 现象Agent 想把答辩结论写入记录，但保存失败。
  2. 可能原因接口没开、权限不够、字段格式错或状态冲突。
  3. 工具可修如果是接口或权限问题，先修工具层。
  4. 工具不可修如果只是展示问题，不该调用写入动作。

动作与权限边界：先知道谁能做、会改什么

工具调用前要先明确权限和状态边界。动作不是“能点按钮”这么简单，而是要知道会改哪些字段、产生哪些后果。

权限

状态

回执

白话解释

动作边界像工作台上的开关：先看这个开关能不能按、按下去会不会改别的东西。

它不等于什么

它不是只要有 API 就能放心用，也不是动作越多越好。

危险写法有接口就直接调，别管会改什么

不看状态影响，后续会难以回滚和排查。

更稳的写法先看权限和状态，再决定是否调用工具

知道动作会改什么，后面才能治理。

完整示范：更新答辩结果前先看什么权限和状态要先清楚
  1. 权限当前角色是否能写入该记录。
  2. 状态写入后会不会覆盖已有结论。
  3. 回执如何把结果回给用户或日志。
  4. 产品动作动作前先检查权限和状态边界。

Prompt / 工具 / 数据 / 人工分界：把职责拆开，Agent 才好治理

Prompt 负责判断与表达，工具负责执行，数据负责保存，人工负责高风险确认。今天要把这四层分开。

0 / 2 步
白话解释

把 Agent 想成一个小系统：Prompt 负责说清楚，工具负责去做，数据负责记下来，人工负责拍板。

它不等于什么

它不是把全部职责塞进同一个层里，也不是让模型替代工具。

危险分工执行、展示和正式确认混在一起

一出错就不知道该回滚哪一层。

可治理分工Prompt 判断 → 工具执行 → 数据落库 → 人工确认

职责分开后，才能评测、日志和回滚。

完整示范：保存答辩记录应该怎么分层先分层，再实现
  1. Prompt判断是否需要保存以及输出说明。
  2. 工具真正写入记录。
  3. 数据保存字段、版本和状态。
  4. 人工确认是否作为正式结论。
