留下一个理解或疑问

前端状态是不是用户点到哪儿就算产品到哪儿？

前端状态可以先理解为“把服务端事实投影给用户看的界面”。页面可以有 loading、draft 和 error，但真正的 session、权限、文件处理进度和 AI 结果必须由服务端事实支撑。

0 / 2 步

View State

就是页面正在展示什么

例如正在上传、检索中、答案已生成、需要重试。

能决定：用户看到什么不能决定：服务端事实

Server State

就是服务端保存的真实业务状态

例如 session_id、document_id、job_status、answer_id。

能决定：下一步允许什么不能被页面猜测覆盖

Draft State

就是还没提交的用户输入

例如问题草稿、筛选条件、临时表单。

能保存在当前页面不能当作正式记录
白话解释

前端像驾驶舱仪表盘，显示速度和故障灯；它不应该自己假装发动机已经修好。AI Demo 里，页面要诚实显示服务端状态，而不是靠按钮点击本地改成“完成”。

它不等于什么

它不等于 localStorage 里的万能真相，也不等于 URL hash、按钮颜色或动画进度。页面状态不能反向制造服务端完成。

看起来合理，但错误点击生成 → 本地标记 answer_ready

如果服务端还在检索或失败，页面会展示假的成功。

正确的产品链路用户动作 → 服务端状态 → 前端投影 → 用户下一步

页面只展示已确认事实，并保留草稿和错误恢复入口。

完整示范：文档上传后卡住先查服务端 job

现象：用户上传文档后，前端 2 秒后自动显示“索引完成”。

  1. 已知事实服务端 job_status 仍是 processing，索引还没有可检索片段。
  2. 第一个错误节点用本地计时器替代服务端状态。
  3. 正确动作页面轮询或订阅 job_status；未完成时显示处理中，可取消或稍后恢复。
  4. 保持不变所有会影响下一步权限的状态，都以服务端事实为准。

留下一个理解或疑问

为什么不能让前端直接调用模型或向量库 API？

安全代理可以先理解为“你自己的服务端接待台”。前端只交业务请求，服务端核对身份、权限、额度、日志白名单和敏感字段，再决定是否调用模型、向量库或内部 API。

0 / 2 步

API Proxy

就是前端和外部服务之间的服务端门口

统一处理认证、限流、日志、错误和响应格式。

能保护：密钥和业务规则不能跳过：权限校验

Environment Secret

就是只在服务端环境变量里的秘密

例如模型 Key、向量库 Key、内部服务 Token。

能用于：服务端调用不能下发：浏览器

Allowlist Log

就是只记录允许记录的字段

保留排错信息，但不写入 Key、身份证、完整隐私文本。

能帮助：调试不能保存：敏感明文
白话解释

前端是公开空间，服务端才是保管钥匙和执行业务规则的地方。安全代理不是多绕一层，而是让秘密、权限、成本和审计都有一个可控入口。

它不等于什么

它不等于简单转发，也不等于把所有请求原样打印到日志。代理层如果不校验权限，只是把风险从前端搬到后端。

看起来合理，但错误Browser → OpenAI / Vector DB

Key、索引名和内部数据范围都可能暴露，且无法统一限流和审计。

正确的产品链路Browser → Server API → Provider/RAG Adapter

服务端先核对用户、文档权限和额度，再调用外部服务。

完整示范：向量库 Key 泄露风险先阻断前端直连

现象：Demo 为了省事，让浏览器带向量库 Key 直接查询企业知识库。

  1. 已知事实用户能在网络面板看到 Key 和索引请求，可能查询不属于自己的文档。
  2. 第一个错误节点把浏览器当成可信调用方。
  3. 正确动作前端只提交 question 和 document_id；服务端核对权限后用环境变量调用向量库。
  4. 保持不变任何外部服务密钥和内部数据边界都必须由服务端代理守住。
理解检查：前端能不能直连向量库

RAG Demo 为了赶进度，计划把向量库 Key 放到浏览器里直接检索。第一步应该怎么处理？

留下一个理解或疑问

RAG 是不是把文档塞给模型就行？

RAG 可以先理解为“先找资料，再让模型只依据找到的资料回答”。真正的接入不只是上传文档，还要切块、索引、检索、重排、引用和无证据处理。

0 / 2 步

Chunk

就是把大文档切成可检索小段

每段要保留来源、标题、页码或位置。

能帮助：精准检索不能丢失：来源信息

Retrieval

就是按问题找候选资料

可能用关键词、向量或混合检索。

能提供：候选证据不能证明：答案已正确

Grounded Answer

就是答案能回到资料原文

回答绑定 quote、source 和 limitation。

能发布：有证据结论不能编造：未检索到的信息
白话解释

RAG 像开卷考试：先从资料里找到相关段落，再根据段落答题。没有找到资料时，正确动作不是让模型猜，而是告诉用户当前资料不足。

它不等于什么

它不等于把整份 PDF 塞进 Prompt，也不等于“接了向量库就一定可信”。检索结果差时，模型仍可能答得流畅但没有依据。

看起来合理，但错误上传 PDF → 全文进 Prompt → 模型总结

上下文爆炸、来源不可回放，答案超出材料也难发现。

正确的产品链路切块带来源 → 检索候选 → 筛证据 → 带引用回答

每个结论都能回到具体片段。

完整示范：员工手册问答先看资料是否命中

现象：用户问“试用期请假怎么扣薪”，检索结果只命中年假制度。

  1. 已知事实候选片段没有覆盖试用期请假扣薪。
  2. 第一个错误节点用相近制度让模型推断答案。
  3. 正确动作返回资料不足，展示已命中片段，并提示需要补充试用期或薪酬政策。
  4. 保持不变RAG 答案范围不能超过检索到的可引用资料。

留下一个理解或疑问

模型输出结构对了，Demo 就能继续往下走吗？

结构校验可以先理解为“机器能不能安全接住这份输出”。它要检查 JSON 形状、字段范围、引用是否存在、状态是否允许；失败时要有限重试或安全降级。

0 / 2 步

Schema Check

就是检查输出形状

字段是否存在、类型是否正确、枚举是否允许。

能发现：格式错误不能发现：事实越界

Business Validation

就是检查业务事实

引用是否来自文档、分数是否有依据、状态是否允许。

能阻止：错误写入不能交给：模型自证

Degrade Path

就是失败后的诚实出口

保留输入和 request_id，说明失败类型，允许重试或人工处理。

能保护：用户事实不能伪造：成功结果
白话解释

模型输出像外部寄来的包裹：先看包装完整，再看内容有没有错、能不能入库。包裹坏了不能无限重寄，也不能把空包裹登记成已入库。

它不等于什么

它不等于“try/catch 后弹一个错误”。也不等于失败后随便返回默认答案。恢复链要保留原输入、限制重试次数，并明确告诉用户什么没有完成。

看起来合理，但错误JSON parse 成功 → 写入答案

可能把无引用、越权状态或不在枚举里的业务结论写进去。

正确的产品链路结构校验 → 业务校验 → 有限重试 → 降级/人工

每一步失败都有明确停止条件和用户出口。

完整示范：答案缺少引用不要用空引用发布

现象：模型返回 JSON 合法，但 citation_ids 为空，答案却给出确定结论。

  1. 已知事实结构合法；证据链缺失；用户问题仍需要可引用答案。
  2. 第一个错误节点把 JSON 合法当成可发布。
  3. 正确动作拒绝发布该结论，尝试一次重新检索或重试；仍失败则返回资料不足。
  4. 保持不变格式通过只是第一关，业务证据和状态权限必须单独校验。
理解检查：结构合法但证据缺失怎么办

AI Demo 返回合法 JSON，但答案没有任何引用，且检索结果为空。第一步应该怎么处理？
