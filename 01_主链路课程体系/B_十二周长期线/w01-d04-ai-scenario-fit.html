先把 Prompt 从“话术”升级成产品任务契约

Prompt 不是灵感句子，而是 Agent 每一步可复用、可测试、可协作的任务说明。

今天不追求万能提示词。你会学习 AI PM 如何把“请帮我高频面试追问”拆成角色、输入、输出、判断标准和失败处理，让 Prompt 成为产品方案的一部分。

今天学什么AI 场景适配的职责：判断任务、价值、风险、数据和决策口径。
今天不学什么不背场景清单，不追逐玄学判断，也不进入 RAG、工具调用或工程调参。

错误直觉写得越长越专业 = Prompt 越好

指令很完整，但没有说明输入来源、输出结构、失败兜底和验收口径。

正确判断目标、输入、输出、评价可复用 = Prompt 可产品化

Prompt 能被团队复查、被样例测试、被版本迭代，才是产品资产。

Prompt 的产品定义：把模型调用写成任务契约

AI PM 不只写“让模型说什么”，还要定义模型为什么被调用、拿什么输入、产出什么、由谁检查和失败时怎么办。

白话解释

Prompt 像一份给模型的任务说明书，告诉它在这个产品步骤里该做什么、不能做什么。

它不等于什么

不是一段越长越好的咒语，也不是把产品责任交给模型自由发挥。

目标

本次调用要达成什么

例如高频追问、价值密度证据缺口、可控风险回答建议。

必须可验证，不写空泛目标

约束

哪些材料可用、哪些事禁止

说明可读取的 JD、项目回答和历史状态，禁止补造事实。

继承 W1D2 的场景判断

验收

输出怎样才算可用

字段完整、引用来源、覆盖 Rubric，并能被程序或人工检查。

为后续 Eval 留入口
完整示范：高频项目答辩追问从一句需求改成任务契约

原始需求：“帮用户高频几个面试追问。”

  1. 场景任务发现项目经历中缺失的职责、动作、指标和复盘证据。
  2. 可用输入JD、用户项目描述、当前回答、已标记的证据缺口。
  3. 输出要求返回 3 个追问，每个追问带目标证据标签和不能追问的原因边界。
  4. 失败处理材料不足时不高频虚假追问，而是提示需要用户补充项目背景。

价值信号：Prompt 先决定模型可以看见什么

同一句 Prompt，给不同上下文会得到完全不同输出。AI PM 要定义上下文来源、优先级、缺失信息和隐私边界。

0 / 2 步
白话解释

Prompt 不只是指令，还包括模型拿到的材料包。材料包混乱，输出就会看似合理但无法引用。

它不等于什么

把所有用户资料都塞进去不等于上下文充分，反而可能引入冲突、泄露和噪声。

危险写法请根据用户所有信息给出追问

模型不知道哪些材料最新、哪些可信、哪些不能用于本次问题。

契约写法只使用当前回答、JD 和已标记缺口

上下文范围可追溯，输出能解释为什么追问这个点。

完整示范：追问前的上下文包让模型只看该看的材料
  1. 必要输入当前问题、用户回答、JD 要求、项目材料和已知缺口。
  2. 优先级用户最新回答优先于历史草稿；JD 能力要求优先于泛化面试建议。
  3. 缺失表达没有结果指标时标记未知，不允许模型用常见指标补齐。
  4. 隐私边界不把不相关的个人资料放进本次追问上下文。

Agent 要高频“项目结果追问”，应该给模型什么上下文？

需要提示时展开

如果这个输入无法解释输出为什么产生，就不要放；如果缺了会导致模型乱补，就必须标记。

上下文设计已记录。

高频追问的上下文包：必须输入当前回答、JD 能力点、项目材料和缺口标签；可选输入历史追问；禁止输入无关个人资料；缺少结果指标时输出补证追问。

输出 Schema：让 Prompt 产出能被产品继续使用

如果输出只是自然段，后续很难校验、排序和复用。Prompt 要提前定义字段、类型、数量、引用和不确定性表达。

0 / 2 步
白话解释

Schema 像一个表格模板，让模型的回答能被页面、后端、日志和评测继续处理。

它不等于什么

不是为了显得工程化而加 JSON，而是为了让输出可检查、可比较、可回放。

字段

每个结果必须有什么

追问文本、目标证据、引用来源、风险标签。

字段缺失就不能进入下一步

数量

避免无限发散

例如固定返回 3 条追问，每条只针对一个证据缺口。

方便页面展示和评测

不确定

明确未知和待补证

没有来源时输出 unknown_reason，而不是补写答案。

接住 W1D2 的边界
完整示范：追问候选 Schema让输出能进入产品流程

字段：question、target_evidence、source_quote、risk、follow_up_if_missing。

  1. question给用户看的追问文本，不能同时问多个问题。
  2. target_evidence说明这条追问要补职责、动作、结果还是复盘。
  3. source_quote绑定触发追问的用户原话或 JD 要求。
  4. risk标记事实不足、表述空泛或结果缺失，供后续 Rubric 使用。

Rubric 与口径：Prompt 要说明什么叫“好输出”

没有评价口径，Prompt 只能靠感觉迭代。AI PM 要把好追问、坏追问和边界情况写成可判断标准。

0 / 2 步
白话解释

Rubric 是评判输出质量的尺子，告诉模型和团队什么算合格、什么必须退回。

它不等于什么

不是“更专业、更具体”这种主观形容，而是能拿样例逐条判断的标准。

模糊口径追问要专业、有深度

不同人会给出完全不同的判断，模型也不知道优先补什么证据。

可评口径每条追问只补一个证据缺口，必须引用触发来源

可以直接检查输出是否合格，并收集 badcase。

完整示范：好追问的 4 条标准把口味变成规则
  1. 相关追问必须对应 JD 或项目材料中的真实缺口。
  2. 单一一条追问只问一个证据点，避免用户不知道答哪部分。
  3. 可回答问题应要求用户补事实、动作或结果，而不是空泛自评。
  4. 不越界不诱导用户编造数据，不替用户确认经历真实性。
理解检查：哪条 Rubric 可执行

为 Agent 的追问或反馈输出写三条合格标准，并各补一个反例。

需要提示时展开

标准最好能回答：看什么字段、怎样算通过、失败时怎么改。

Rubric 草稿已记录。

示例：追问必须引用来源；一条只补一个缺口；不能诱导编造数字。反例包括“你觉得自己最大的成功是什么”这种无来源、泛化、不可评的追问。

Prompt 迭代：用 badcase 改契约，而不是凭感觉改词

Prompt 不是一次写完。每次失败都要记录输入、输出、违反了哪条口径、下一版怎么改，以及怎么验证是否真的变好。

0 / 2 步
白话解释

Prompt 迭代像产品实验：先定义问题，再改一个变量，最后用样例验证。

它不等于什么

不是看到输出不满意就随手加“请更专业、更准确、更详细”。

Badcase

失败输入和失败输出

保留触发失败的材料和模型原始输出。

归因

是哪条契约缺失

目标、上下文、Schema、Rubric 或边界哪一项没写清。

验证

下一版怎样证明有效

用同一批样例复测，不只看一个新输出。

完整示范：追问过于泛化从失败样例回到契约

Badcase：模型输出“你在项目中遇到的最大挑战是什么？”但没有引用 JD 或项目缺口。

  1. 失败归因Rubric 没要求追问必须绑定一个证据缺口。
  2. Prompt 修改新增字段 target_evidence 和 source_quote，并要求每条追问只补一个缺口。
  3. 复测样例用同一段空泛项目经历再次高频，检查三条追问是否都绑定来源。
  4. 保留记录写清版本、修改原因和仍未解决的问题，方便后续 Eval Set 使用。
理解检查：哪种迭代方式更可靠

当 Prompt 高频的追问太泛时，应该怎么改？

带着项目做一次：写一条 Prompt 迭代记录

假设 Agent 高频了一个泛化追问，写出 badcase、失败归因、改动点和复测方式。

需要提示时展开

不要只写“优化 Prompt”；必须写改哪一条契约，以及怎么判断新版本通过。

迭代记录已保存。

示例：Badcase 是追问“你最大的挑战是什么”；归因是未要求绑定证据缺口；改动是新增 source_quote 和 target_evidence；复测同一项目材料，要求三条追问都引用来源且各补一个缺口。
