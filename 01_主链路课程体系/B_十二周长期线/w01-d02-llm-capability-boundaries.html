先建立一个不会被演示效果骗走的模型

LLM 不是事实数据库，而是根据上下文预测下一段语言。

这个定义决定了 AI PM 的第一个产品边界动作：不要问“模型聪不聪明”，要问“这一步需要生成、判断、记忆、执行还是承担责任”。

今天学什么识别生成、总结、改写、分类和开放式建议等模型能力。
今天不学什么不进入 Prompt 结构、RAG 实现或 API 细节，那些留给 W01-D03 及后续课程。
今天留下什么《Agent 模型能力边界表 v1》：每项任务都写清适配度、禁止事项、校验方式和失败兜底。
材料与任务先明确输入是什么

JD、项目经历、回答和训练目标共同决定模型需要处理的上下文。

→
模型生成只提出语言候选

生成问题、追问、总结或建议草稿，不自动确认事实或状态。

→
校验与边界再决定能否使用

检查来源、格式、规则、权限和风险，把不确定性保留下来。

→
用户行动确认、补证或继续

用户选择追问、补充材料、修改回答或接受下一步训练。

理解：说明模型能做什么、不能保证什么。判断：把生成候选与事实、状态、权限分开。应用：为 Agent 的具体任务写模型、规则、用户和人工分工。迁移：换成简历优化或知识库场景，仍保留同一边界。
错误直觉模型输出 = 真实结论

只要回答完整、语气自信，就把它展示为用户事实或正式评分。

正确判断模型输出 = 待校验的语言候选

输出先进入结构、来源、规则和人工确认环节，再决定能否影响 Agent 状态。

LLM 擅长什么：把开放式语言工作交给模型

当输入上下文明确、允许多个合理答案、结果还需要人或规则检查时，模型适合生成候选、总结材料、改写表达和提出建议。

0 / 2 步
白话解释

模型像一个能快速续写和重组语言的助手，能从给定材料里提出很多可能的表达。

它不等于什么

会生成一段像样的话，不等于这段话真实、完整、合规或可以直接执行。

生成

提出问题和建议候选

基于 JD、项目经历和训练目标生成追问候选。

需要：上下文、任务目标、输出范围仍需：规则筛选和用户确认

总结

压缩已有材料

把多轮回答整理成能力证据和改进方向草稿。

需要：来源材料和摘要目标仍需：检查遗漏与引用

改写

改善表达方式

把用户已有事实改写成更清晰的项目回答。

需要：原始事实和表达限制仍需：禁止凭空增加结果
完整示范：生成追问候选先看适配度，再看控制方式

任务：用户说“我负责了项目增长”，Agent 需要继续追问。

  1. 适合交给模型根据职责、动作、对象和结果缺口，生成 3 个不同方向的追问候选。
  2. 不能直接交给模型判断用户是否真的负责增长，或把用户没有说过的增长数字写进报告。
  3. 外部约束追问候选必须绑定已有材料中的缺口；输出经过 Schema 检查后再展示。
  4. 用户动作用户选择或回答追问，Agent 再把新增信息作为下一轮上下文。

留下一个理解或疑问

LLM 为什么会说得像真的：流畅性和事实性是两件事

模型根据上下文预测高概率表达，可能把缺失信息补成完整句子。AI PM 要把“有来源的事实”“用户未提供的信息”和“模型推测”分开。

0 / 2 步
白话解释

模型能把空白填得很顺，但它不知道这个空白在现实中是否发生过。

它不等于什么

写得具体、语气确定、数字完整，都不能替代原始材料或用户确认。

危险写法“项目增长 30%”

用户只说“负责增长”，模型为了让回答完整而补出数字。

边界写法“增长结果：未提供；需要追问来源”

把缺失事实显式标记出来，继续训练证据，而不是替用户制造证据。

完整示范：处理空泛项目经历不确定性必须可见

输入：“我负责了一个推荐项目，效果很好。”

  1. 已知事实只知道项目名称和用户的主观评价。
  2. 第一个错误节点模型直接生成提升比例、实验周期和个人贡献。
  3. 正确动作标记结果和职责缺口，生成追问：负责哪一段、用什么指标、对比基线是什么。
  4. 保持不变没有来源的信息维持“未知”，不能被流畅语言升级成事实。
理解检查：哪种输出更可信

项目材料没有提供数据时，Agent 应该怎样处理？

带着项目做一次：给事实加状态标签

从 Agent 的项目材料中任选三句话，分别标记为“有来源事实”“用户主张待确认”“模型建议”，并写出下一步。

需要提示时展开

标签的目的不是让输出更复杂，而是让后续评分和报告知道哪些内容能引用。

方案已记录。

“负责推荐项目”可记录为用户主张待确认；“项目使用的 JD”可作为用户材料事实；“建议追问对比基线”属于模型建议。只有前两者有明确来源时，报告才可以引用。

留下一个理解或疑问

模型、规则、程序和用户：谁有权决定下一步？

LLM 可以提出语言判断，但不天然拥有写状态、判定通过或确认真实性的权限。越接近不可逆动作，越要把决定拆给规则、程序和人。

0 / 2 步
白话解释

模型负责“提议”，系统负责“检查和执行”，用户或人工负责“确认承担后果的判断”。

它不等于什么

加一个模型调用就不等于拥有完整的业务流程、权限控制和责任链。

模型

生成候选与解释草稿

问题、追问、摘要、建议和可能的证据缺口。

不能：直接写入通过状态

程序 / 规则

检查约束与推进允许状态

Schema、必填字段、评分门槛、重复提交和状态转换。

不能：替代开放式表达和复杂语境理解

用户 / 人工

确认事实和敏感结论

确认项目经历、补充证据、接受或修改建议。

不能：被模型伪造确认记录
完整示范：处理“是否通过答辩”把建议与状态分开

模型输出：“回答结构完整，但结果证据不足，建议补充基线。”

  1. 模型负责给出基于当前回答的反馈候选，并指出引用的材料片段。
  2. 规则负责检查必填评分维度是否都有输入，决定是否允许进入“待确认”状态。
  3. 用户 / 人工负责确认事实、修改回答或决定是否结束训练。
  4. 保持不变反馈文本可以由模型生成，正式状态转换不能只由自然语言触发。
理解检查：哪项分工更稳妥

Agent 生成“建议通过”的评分草稿后，下一步应该是什么？

带着项目做一次：给 Agent 任务分配责任人

为“生成追问”“判断资料是否足够”“写入答辩通过”“允许用户修改回答”四项任务分别指定模型、规则 / 程序、用户 / 人工，并写出理由。

需要提示时展开

先问这项任务是否需要开放式语言，再问它是否会改变状态、确认事实或承担风险。

方案已记录。

生成追问：模型提出候选；判断资料是否足够：规则检查必填字段，模型可解释缺口；写入答辩通过：规则和用户 / 人工确认；允许用户修改回答：用户负责。每项都要记录来源和状态变化。

留下一个理解或疑问

Agent 不是“会聊天”：模型要嵌在可回放的流程里

一个可靠的 Agent 至少要知道当前任务、已有材料、允许调用的步骤、输出格式和失败后的去向。今天只建立流程边界，不展开 W2 的工具选型。

0 / 2 步
白话解释

Agent 是一条有状态的工作流，模型是其中一个可以替换的处理节点。

它不等于什么

多轮对话、自动调用模型或一句“让 Agent 自主完成”，都不能替代输入输出和失败规则。

聊天直觉用户说一句 → 模型自由决定下一步

流程、权限、失败和历史都藏在自然语言里，无法稳定回放。

Agent 边界状态 → 上下文 → 模型 → 校验 → 允许的状态转换

每个节点都能回答输入是什么、输出是什么、失败时怎么办。

完整示范：一次追问请求先读状态，再调用模型
  1. 读取状态确认 session、当前问题、用户已有回答和缺失证据。
  2. 准备上下文只把完成本次追问所需的材料交给模型。
  3. 生成候选模型返回追问文本和目标证据标签。
  4. 校验与记录程序检查格式和允许状态，再记录 request_id 与结果；失败时回到可重试状态。
理解检查：哪项最像 Agent 流程

需要提示时展开

不要写 Prompt 句子；今天关注的是流程节点和责任边界。

方案已记录。

生成追问：调用前读取当前问题、回答和证据缺口；模型输出追问候选和目标标签；调用后检查字段、长度和引用；失败回到“待生成追问”并记录失败原因。

留下一个理解或疑问

今日的《Agent 模型能力边界表 v1》应该写到什么程度？

今天不是判断哪个模型最强，而是为 Agent 每项任务写清模型能贡献什么、不能承担什么，以及出现不确定时谁来校验和兜底。

0 / 2 步
白话解释

边界表是一张职责地图，帮助团队在看到 Demo 效果后仍知道哪里必须加规则、证据和确认。

它不等于什么

“模型很强”或“模型不能保证事实”都太粗，不能直接指导 Agent 的产品设计。

任务

Agent 要完成什么

写生成追问、总结回答、判断资料完整度等具体任务。

模型适配度

为什么适合或不适合

写开放式语言、上下文依赖、事实风险和结果可检查性。

边界与兜底

不能做什么、谁来校验

写禁止自动补事实、禁止直接推进状态，以及规则、用户或人工动作。

完整示范：一行合格记录从能力回到职责

任务：生成项目答辩追问。模型贡献：根据已有材料提出多个追问候选。不能承担：确认用户是否真的完成该项目。校验与兜底：绑定材料缺口、检查输出结构，资料不足时提示用户补充。

  1. 已知事实任务需要开放式语言，但涉及事实和后续状态。
  2. 第一个错误节点把“能生成追问”扩展成“能确认经历真实性”。
  3. 正确动作把模型贡献、禁止事项、校验方式和失败兜底写在同一行。
  4. 保持不变任何模型能力都要同时记录正向用途和反向边界。
