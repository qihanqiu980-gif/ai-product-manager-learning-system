先在脑中搭起一张图：AI 产品运营不是“上线后继续优化”，而是让团队每周知道该看什么、改什么、停什么。

把 W15 理解成团队的 AI 产品操作系统：固定运营节奏收集事实，用小批量增长实验验证假设，用质量监控发现坏案例，用成本容量守住单位经济，用治理评审控制风险，最后把多个机会放进路线图做取舍。

先讲节奏，再讲动作

没有固定节奏，质量、增长和风险都会变成零散救火。

用实验替代愿望

增长不是喊目标，而是一次只验证一个假设，并记录失败时下一步。

把治理放进运营

风险、成本和权限不是上线前文档，而是每周复盘时必须被看见的事实。

Cadence固定运营节奏

负责让团队每周看同一组事实和决策。

→
Experiment小批量增长验证

负责把机会变成假设、样本、指标和停止条件。

→
Monitor质量成本风险监控

负责发现坏案例、成本异常和越权风险。

→
Portfolio路线图取舍

负责把多个 AI 机会按价值、风险和能力放进下一阶段。

定节奏做实验看质量管成本复盘路线图

团队运营节奏是不是每周开会同步一下进展？

运营节奏可以先理解为“固定时间看固定事实，并做固定类型的决定”。它不是例会日历，而是让团队知道哪些指标、坏案例、成本和风险必须被看见。

0 / 2 步

Operating Cadence

就是团队固定复盘节奏

每周或每两周看同一组事实，决定继续、停止、扩大或补数据。

能帮助：减少随机优化不能替代：真实业务判断

Decision Log

就是决策记录

记录当时看到什么、决定什么、谁负责和下次看什么。

能保留：判断依据不能证明：结果一定正确

Escalation Rule

就是什么时候升级处理

例如隐私风险、成本超阈值、质量连续下降时谁被叫进来。

能保护：团队边界不能自动解决：根因分析
白话解释

AI 产品上线后，团队很容易今天改 Prompt、明天补知识库、后天换模型。运营节奏的作用是把这些动作放回同一张桌子：看事实、做决定、记录下次验证。

它不等于什么

它不等于开会越多越好，也不等于每个人汇报自己忙了什么。没有可观察事实和决策记录的会，只是在同步情绪。

看起来协作，但错误每周同步：大家说说最近做了什么

听起来忙，不能回答质量、增长、成本和风险到底变了没有。

正确的产品链路固定事实 → 异常解释 → 决策记录 → 负责人 → 下次观察

每次运营会都留下可复盘的判断链。

完整示范：AI 客服周运营会先定事实面板

现象：团队每周都说“客服机器人体验还要优化”，但没有看同一组指标。

  1. 已知事实有工单量、人工升级、badcase、token 成本和投诉记录，但分散在不同人手里。
  2. 第一个错误节点把例会当成运营机制，没有固定输入。
  3. 正确动作固定每周看命中率、升级率、重复 badcase、成本阈值和风险事件，并写决策记录。
  4. 保持不变团队运营节奏必须服务决定，而不是服务汇报。
理解检查：运营会第一步定什么

AI 知识助手上线后，团队每周都在说“继续优化”，但没有统一判断依据。第一步应该怎么做？

带着资料做一次：设计一场 AI 产品周运营会

请选择一个 AI 客服、知识助手或销售助手，写出周运营会输入、看板、决策、升级规则和下次观察项。

需要提示时展开

至少覆盖质量、增长、成本、风险和负责人，不要只写会议议程。

方案已记录。现在可以对照示例，检查是否从同步变成决策。

示例：每周三看上周会话量、AI 命中率、人工升级率、重复 badcase、token 成本、隐私拦截和投诉；每项异常必须有 owner；会议只做四类决定：继续观察、修复、扩大试点、停止/回滚。决策记录写入下次复盘。

留下一个理解或疑问

增长实验是不是多试几个入口，看哪个数据好？

增长实验可以先理解为“用小样本验证一个具体假设”。它不是到处改入口，也不是只看好看的转化率，而是先写清谁、在什么场景、为什么会多用、看什么指标、何时停止。

0 / 2 步
白话解释

AI 产品的增长常常来自“更容易触发、更快看到价值、更少出错”。实验要一次只改一个主要变量，否则你不知道到底是入口、提示、结果质量还是用户群变化带来的。

它不等于什么

它不等于把所有按钮都做得更显眼，也不等于挑一个涨了的数字庆祝。没有假设和停止条件的增长，很容易变成噪声。

看起来积极，但错误同时改入口、文案、模型和用户分层

数据变化后无法判断原因，失败也不知道该恢复哪一项。

正确的产品链路用户问题 → 单一假设 → 小样本 → 指标/护栏 → 停止条件 → 复盘

实验先服务学习，再服务扩大。

完整示范：知识助手激活实验先定一个假设

现象：团队想同时改首页入口、默认问题、模型和知识库摘要，希望激活率提升。

  1. 已知事实新用户不知道第一步该问什么，首问转化低。
  2. 第一个错误节点同时改太多变量，无法学习。
  3. 正确动作只测试“按岗位展示 3 个首问模板”是否提升首问率，同时看无答案率和投诉。
  4. 保持不变增长实验要一次验证一个主要假设。
理解检查：增长实验先写什么

你想提高 AI 知识助手激活率，团队提出同时改入口、模板、模型和知识库。第一步应该怎么收敛？

带着资料做一次：写一个增长实验卡

请为一个 AI 产品写增长实验卡：目标用户、假设、单一变量、样本、主指标、护栏指标、停止条件和复盘方式。

需要提示时展开

主指标看增长，护栏指标看质量、风险和成本，停止条件要提前写。

方案已记录。检查是否一次只改一个主要变量。

示例：目标是新客服坐席首周激活；假设是“按工单类型给 3 个首问模板”能降低第一步成本；只改模板入口，不改模型；主指标是首问率，护栏是无答案率、人工升级率、隐私拦截和 token 成本；连续两周无提升或护栏恶化就停止。

留下一个理解或疑问

质量监控是不是看平均满意度和几个 badcase？

质量监控可以先理解为“持续发现系统在哪类场景下失败，并把失败送回修复链”。平均分可能掩盖高风险坏例，单个截图也不能代表整体。

0 / 2 步

Badcase Loop

就是坏案例回路

收集、分类、归因、修复、回归，再看是否复发。

能推动：质量迭代不能证明：所有场景安全

Quality Slice

就是分场景看质量

按用户、任务、知识来源、模型版本或风险等级切开。

能发现：局部失败不能替代：根因分析

Regression Check

就是修完后再测旧问题

防止修一个场景又破坏另一个场景。

能保护：稳定性不能保证：永不再错
白话解释

AI 产品质量不是“总体看还行”。你要知道哪些用户、哪些问题、哪些知识源、哪些模型版本容易错；修完以后，还要看旧坏例有没有复发。

它不等于什么

它不等于只看平均满意度，也不等于把几个精彩截图当证据。高风险小样本坏例需要单独被看见。

看起来稳定，但错误平均满意度 4.5 → 质量没问题

平均数可能掩盖隐私、幻觉、过期信息和高价值客户失败。

正确的产品链路分场景质量 → badcase 归因 → 修复 → 回归 → 复发监控

质量监控要能驱动下一步修复。

完整示范：高价值客户错答先切片看质量

现象：整体满意度不错，但企业版客户多次遇到合同条款错答。

  1. 已知事实总体指标好，高价值客户合同场景失败集中。
  2. 第一个错误节点用平均满意度掩盖高风险切片。
  3. 正确动作按客户类型和任务类型切片，建立合同场景 badcase 回路和回归集。
  4. 保持不变AI 质量要看切片、根因和复发，不只看平均数。
理解检查：平均分很好还要看什么

AI 客服平均满意度很高，但大客户合同问题反复错答。第一步应该怎么做？

带着资料做一次：设计质量监控切片

请为一个 AI 助手设计质量监控：切片维度、badcase 来源、归因字段、修复责任、回归样本和复发报警。

需要提示时展开

至少覆盖一个高风险切片，不要只写总体满意度。

方案已记录。检查是否能驱动修复和回归。

示例：按客户等级、任务类型、知识源和模型版本切片；badcase 来源包括投诉、人工纠错、无答案、拒答和抽检；归因到知识缺失、检索失败、Prompt 越界、模型幻觉或权限问题；每周回归前 20 个高风险坏例，复发超过阈值就暂停扩大。

留下一个理解或疑问

成本管理是不是月底看一下 token 账单？

成本容量可以先理解为“提前知道每次使用要花多少、增长后会不会撑不住、什么时候该换模型或限流”。AI 成本要和价值、质量、延迟一起看。

0 / 2 步
白话解释

如果每个用户多问一次都要烧钱，增长就不能只看使用量。你要知道单位成本、峰值容量、模型路由、缓存、限流和付费价值之间的关系。

它不等于什么

它不等于越便宜越好，也不等于账单超了再处理。成本管理要提前进入实验和路线图。

看起来增长快，但错误使用量翻倍 → 先庆祝，月底再看账单

可能质量没变好，成本先失控，甚至挤占高价值场景容量。

正确的产品链路单位成本 → 使用峰值 → 路由/缓存 → 价值指标 → 扩大或限流

成本和增长必须一起判断。

完整示范：强模型全量调用先算单位经济

现象：团队把所有问题都切到强模型，答复质量略升，但 token 成本翻三倍。

  1. 已知事实质量提升集中在复杂问题，简单问题也用了强模型。
  2. 第一个错误节点只看质量平均提升，没有看单位成本和任务分层。
  3. 正确动作按任务复杂度做模型路由，简单问题用低成本路径，复杂问题用强模型。
  4. 保持不变AI 产品扩大前必须知道单位成本和容量上限。
理解检查：成本涨了怎么办

使用量和账单同时快速上涨，但复杂问题质量确实更好。第一步应该怎么判断？

带着资料做一次：写成本容量表

请为一个 AI 产品写成本容量表：任务分层、模型路径、单位成本、峰值容量、限流规则、缓存策略和扩大条件。

需要提示时展开

不要只写省钱，要说明哪些场景值得花强模型成本。

方案已记录。检查是否把成本、质量和价值放在一起。

示例：FAQ 类问题走检索加低成本模型；合同、投诉和高价值客户问题走强模型并人工复核；重复问题缓存；高峰期限制低价值批量请求；扩大条件是复杂问题解决率提升且单位成本低于阈值，护栏是延迟、投诉和隐私拦截。

留下一个理解或疑问

治理评审是不是上线前让法务安全看一眼？

治理评审可以先理解为“在关键决策点确认谁有权批准、哪些风险被看见、哪些场景必须停止”。它不是最后盖章，也不是让风险方背锅。

0 / 2 步

Decision Rights

就是谁有权决定

业务、技术、数据、安全、合规和产品各自能批准什么。

能减少：越权上线不能替代：事实证据

Guardrail Review

就是护栏检查

检查隐私、拒答、人工复核、审计日志和回滚条件。

能保护：可控试点不能保证：模型不会犯错

Stop Rule

就是何时必须停止

触发隐私泄露、误导高风险决策、成本失控或投诉阈值时停用。

能明确：底线不能事后补写：授权
白话解释

AI 产品治理不是“不许做”，而是让团队知道哪些事能自己决定，哪些必须拉上数据、安全、合规或业务负责人。这样试点扩大时才不会靠侥幸。

它不等于什么

它不等于上线前发一封邮件，也不等于写了风险清单就自动合规。治理要绑定决策权、护栏和停止规则。

看起来省流程，但错误业务说要 → 产品直接扩大到全量

遗漏数据权限和安全评审，风险事件出现后无法解释谁批准了什么。

正确的产品链路决策权 → 风险证据 → 护栏检查 → 批准/限制 → 停止规则

治理评审要在扩大前发生。

完整示范：从内部试点到客户可见先补决策权

现象：内部知识助手效果不错，业务希望直接开放给客户使用。

  1. 已知事实内部试点通过，不代表客户可见场景的权限、日志和拒答都合格。
  2. 第一个错误节点把内部试点授权当成外部发布授权。
  3. 正确动作组织治理评审，确认数据范围、客户可见答案、审计日志、人工复核和停止规则。
  4. 保持不变扩大范围时必须重新确认决策权和护栏。
理解检查：内部试点能不能直接外放

内部 AI 助手表现不错，业务想直接开放给客户。第一步应该怎么做？

带着资料做一次：写治理评审清单

请为一个 AI 助手从内部试点扩大到客户可见场景，写治理评审清单：谁批准、看什么证据、哪些护栏、什么情况停止。

需要提示时展开

至少写出业务、技术、数据、安全/合规、产品各自的决策边界。

方案已记录。检查是否把治理变成可执行决策。

示例：业务 owner 批准客户范围；数据 owner 批准字段和脱敏；技术 owner 批准接入、日志和回滚；安全/合规批准拒答、审计和隐私处理；产品 owner 维护护栏和停止规则。触发隐私泄露、错误建议高风险动作或成本超阈值时暂停扩大。

留下一个理解或疑问

路线图复盘是不是把所有 AI 想法排个优先级？

路线图组合复盘可以先理解为“把多个 AI 机会放在同一张取舍表里”。不是谁声音大谁先做，也不是每个场景都 AI 化，而是看价值、证据、风险、成本、能力和时机。

白话解释

当团队有多个 AI 想法时，你要能说清：哪个是增长机会，哪个是质量修复，哪个是风险治理，哪个只是技术好奇。路线图不是待办清单，而是资源取舍。

它不等于什么

它不等于把所有需求排成从 1 到 20，也不等于为了显得 AI 化而铺满场景。没有证据的机会要先补验证，不直接进大项目。

看起来全面，但错误所有业务线都加 AI 助手

资源分散，质量、成本和治理能力跟不上。

正确的产品链路机会分类 → 证据强度 → 价值/风险/成本 → 能力约束 → 路线图决策

把 AI 机会当组合管理。

完整示范：三个 AI 机会怎么排先看证据和约束

现象：团队同时想做客服摘要、销售话术生成和合同审核助手。

  1. 已知事实客服摘要已有 badcase 和指标，销售话术只有想法，合同审核风险高。
  2. 第一个错误节点按需求方声音大小排序。
  3. 正确动作客服摘要进入扩大试点，销售话术先做小实验，合同审核先做治理和人工复核方案。
  4. 保持不变路线图要同时看价值、证据、风险、成本和能力。
理解检查：多个 AI 机会怎么排

客服摘要有数据，销售话术只有想法，合同审核价值高但风险大。第一步应该怎么排？

请列出 3 个 AI 产品机会，并为每个机会判断：证据强度、用户价值、风险、成本、依赖能力、下一步队列。

需要提示时展开

下一步不只有“做”，也可以是补数据、小实验、治理评审、暂缓或停止。

方案已记录。检查是否把不同机会放进不同队列。

示例：客服摘要有基线和质量监控，进入扩大试点；销售话术只有假设，先做小样本增长实验；合同审核价值高但风险高，先做治理评审、人工复核和拒答规则，不直接上线。路线图每月根据证据更新。

综合工作坊：把一个混乱的 AI 项目团队，修成可持续运营机制。

这不是记忆测试。你可以回看任意模块、打开提示并修改方案。目标是把运营节奏、增长实验、质量监控、成本容量、治理评审和路线图组合复盘连成一套团队机制。

错误方案：团队每周只同步忙了什么；增长实验同时改多个变量；质量只看平均满意度；月底才看 token 账单；内部试点好就直接客户可见；所有业务线都想加 AI 助手。

请改成：固定事实面板和决策记录、小批量假设实验、分场景 badcase 回路、单位成本和容量规则、扩大前治理评审，以及按证据和风险分层的路线图。
工作坊路线：不知道从哪里开始时按这五步走
  1. 节奏团队每周看哪些固定事实，并做哪几类决定？
  2. 实验下一个增长假设是什么，只改哪个变量？
  3. 监控质量、成本和风险分别怎样被看见？
  4. 治理扩大范围前谁批准，哪些护栏和停止规则必须成立？
  5. 路线图多个 AI 机会分别进入扩大、实验、治理、暂缓还是停止？
保存前核对：我的机制是否覆盖

W15 团队运营机制已保存。

网页只检查结构覆盖，不代替真实增长、线上指标、团队绩效、管理审批、客户背书、商业结果或正式掌握证据。现在可以对照示例，挑一处继续补强。

  1. 每周固定看会话量、激活、质量切片、badcase、token 成本、风险事件和决策记录。
  2. 增长实验只测试“按岗位展示首问模板”，主指标是首问率，护栏是无答案率、升级率、投诉和成本。
  3. 质量按客户等级、任务类型和知识源切片，badcase 进入归因、修复和回归。
  4. 成本按任务分层做模型路由和限流，扩大前通过数据、安全、技术和业务治理评审。
  5. 路线图把客服摘要扩大试点，销售话术做小实验，合同审核先治理，不把所有业务线同时 AI 化。
