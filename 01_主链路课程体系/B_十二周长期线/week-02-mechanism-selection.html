先在脑中搭起一张图：选型不是猜哪个技术先进。

把 W2 想成一次产品方案评审：先看用户问题，再看事实在哪里，然后判断模型需要什么信息、谁负责查资料、谁负责限制结论，最后把取舍写进方案记录。

先讲产品动作，再讲术语

每个英文词都先回答“它在产品流里帮谁做什么判断”。

用错误方案划边界

不把“模型更强”“数据更多”当答案，而是指出第一个会失败的产品节点。

带着资料做选型

可以回看解释和提示，目标是写出可辩护的方案取舍，而不是背术语。

用户任务到底要解决什么问题

负责限定答案是摘要、问答、分类、推荐、流程动作还是审核。

→
事实位置答案依据在哪里

负责判断事实在用户输入、知识库、历史样本、规则表还是外部系统。

→
候选机制让模型拿到什么信息

负责比较 Prompt、检索增强、规则、微调、Agent 和非 AI 方案。

→
取舍记录为什么这样选

负责写清效果、成本、延迟、风险、证据和下一轮验证。

看任务找事实比机制写取舍记录疑问

模型“理解文本”到底是在做什么？

先别急着背 Transformer。用产品语言看，它是在把一段文字拆成小片段，根据上下文判断哪些片段互相有关，再预测下一步最可能的输出。

0 / 2 步

Token

就是模型看到的文字小片段

一句话会被切成若干片段。产品上要关心的是上下文长度、输入是否被截断、关键信息是否放进去了。

能影响：上下文占用、成本、遗漏风险不能决定：事实是否真实

Attention

就是模型在当前文本里分配注意力

它帮助模型判断哪些词互相关联。产品上要关心提示是否清楚、证据是否靠近问题、无关内容是否干扰。

能帮助：关联当前输入里的线索不能负责：查找外部事实

Transformer

就是一类擅长处理上下文关系的模型结构

它让模型能在大量文本片段之间建立关系。产品经理不需要推公式，但要知道它依赖“给到它的上下文”。

能做：根据上下文生成候选不能保证：候选一定符合业务规则
白话解释

模型像一个很会接话的读稿人：它会根据你放进稿子里的内容继续写，但它不会自动知道稿子外面的真实事实。

它不等于什么

模型能力强不等于事实都在模型脑子里，也不等于可以省掉检索、规则、校验和业务权限。

看起来先进，但错误换更强模型 → 自动解决事实缺失

事实不在输入和可用知识里时，更强模型也可能只是更流畅地猜。

正确的产品链路任务 → 事实位置 → 上下文供给 → 输出限制

先判断答案需要哪些事实，再决定是否要检索、规则或系统数据。

完整示范：课程助手回答公司政策先问事实在哪里

现象：用户问“我是否能报销这笔培训费”，团队想直接让大模型回答。

  1. 已知事实报销规则在公司制度和用户发票里，不一定在模型参数里。
  2. 第一个错误节点把模型的语言能力当成事实来源。
  3. 正确动作先接入制度和发票字段，再让模型基于证据生成候选解释。
  4. 保持不变换成客服、法务或招聘场景，事实位置仍先于模型选择。
理解检查：用户问政策时第一步是什么

产品要回答“这笔费用能不能报销”。第一步应该做什么？

带着资料做一次：学习助手的事实边界

学习助手要回答“我下一周该补哪类题”。请写出用户任务、事实位置、模型能做什么、程序必须守什么边界。

需要提示时展开

事实可能来自错题记录、学习状态、页面草稿和用户目标。模型可以总结建议，但不能伪造掌握状态。

方案已记录。

先读取错题记录、正式状态和近期页面草稿；模型只能生成“建议补题方向”的候选解释。正式掌握、待复测关系和下一题创建由状态源与 Codex 流程决定，不能让模型凭感觉写入。

留下一个理解或疑问

向量 Embedding 为什么能“找相似”，又为什么不能直接当答案？

Embedding 可以理解为给文本做一张位置卡：意思相近的文本会在这张地图上靠近。它适合找候选材料，但不负责判断材料是否足够、是否过期、是否能直接发布。

0 / 2 步
白话解释

向量检索像在资料库里找“意思相近的几段话”。它帮你缩小范围，不等于已经找到正确答案。

它不等于什么

相似不等于真实；召回不等于覆盖；找到一段相近文字也不等于可以省掉引用、时效和权限检查。

看起来合理，但错误找到最相似段落 → 直接回答

相似段落可能不是最新规则，也可能只覆盖问题的一半。

正确的产品链路切资料 → 找候选 → 重排与过滤 → 标出处 → 限制结论

把检索结果当候选证据，再决定答案能说到哪里。

完整示范：知识库问答命中旧政策先查时效

现象：用户问“试用期请假规则”，检索到一段相似的 2024 年制度。

  1. 已知事实文本相似，但制度可能已更新。
  2. 第一个错误节点把相似度最高当成最新可发布。
  3. 正确动作检查版本、发布时间和适用范围；不足时提示无法确认。
  4. 保持不变任何检索增强都先找候选，再做证据过滤。
理解检查：相似度最高之后还要做什么

系统找到一段非常相似的政策，但没有版本日期。第一步应该怎么处理？

带着资料做一次：客服知识库怎样检索

客服助手要回答退款规则。请设计切资料、找候选、过滤、标出处和无法确认时的回答边界。

需要提示时展开

先写资料怎么切，再写哪些字段会参与过滤，比如版本、渠道、用户地区和订单状态。

方案已记录。

把退款规则按渠道、版本和适用对象切成小段；先用向量召回候选，再按最新版本、地区和订单状态过滤。答案必须标出处和适用范围；如果缺少当前渠道规则，只能说“当前资料不足以确认”。

留下一个理解或疑问

Prompt、检索增强和微调到底分别解决什么问题？

先用白话分清：Prompt 是把要求说清楚；检索增强是临时把外部资料递给模型；微调是用大量样本让模型学会稳定风格或任务模式。

0 / 2 步

Prompt

就是本次任务说明书

适合边界清楚、事实已经在输入里的任务，比如改写、分类、结构化抽取。

能做：限定格式、角色、步骤不能做：补出不存在的事实

RAG

就是先找资料，再带资料回答

RAG 是 Retrieval-Augmented Generation，意思是“检索增强生成”。适合事实在知识库里、还会更新的问答。

能做：接入外部知识不能做：自动保证检索结果正确

Fine-tuning

就是用样本训练模型更像你要的任务

微调适合格式、风格或特定判断模式长期稳定重复，但不适合每天变化的事实。

能做：稳定输出模式不能做：替代实时知识更新
白话解释

Prompt 像现场说明；RAG 像临时把资料夹递过去；微调像长期培训一个助手。三者解决的问题不同。

它不等于什么

不要把所有失败都归因于 Prompt 不好，也不要用微调去记会变的政策。

看起来省事，但错误答案不准 → 先微调

如果原因是缺少最新资料，微调只会把旧事实学得更稳定。

正确的产品链路事实在输入里 → Prompt；事实在资料库 → RAG；模式不稳定 → 微调

先定位失败原因，再选上下文供给方式。

完整示范：售后政策每天更新不要先微调

现象：客服答案经常引用旧规则，团队想收集样本微调。

  1. 已知事实政策每天更新，错误来自知识过期。
  2. 第一个错误节点用微调解决实时事实问题。
  3. 正确动作先做检索增强和版本过滤，再用 Prompt 限制答案边界。
  4. 保持不变会变的事实优先接资料，不优先写进模型参数。
理解检查：政策每天更新时先选什么

客服助手答错主要因为政策每天更新。第一步应该选择什么方向？

带着资料做一次：合同条款助手怎样供给上下文

合同助手要判断条款风险。请说明哪些内容放 Prompt，哪些内容走检索，哪些情况才考虑微调。

需要提示时展开

风险定义和输出格式适合 Prompt；法规、模板和历史案例适合检索；长期稳定的判别风格才考虑微调。

方案已记录。

Prompt 写清风险分类、输出字段和不得越权；检索合同模板、法规条款和已审核案例；如果同类合同长期大量出现且人工标注稳定，再考虑微调判别风格。实时法规仍从检索进入，不写进微调。

留下一个理解或疑问

什么时候应该选规则、RAG、Agent，甚至先不用 AI？

方案选型不是“AI 能做就上 AI”。先看任务是否稳定、事实是否结构化、错误代价多高、是否需要调用工具和跨步骤行动。

0 / 2 步
白话解释

规则像红绿灯，适合边界明确；RAG 像带资料问答，适合知识更新；Agent 像会调用工具的流程助手，适合多步行动。

它不等于什么

Agent 不是“高级聊天机器人”；规则也不是落后方案。错误代价高、条件清楚时，规则往往更可靠。

看起来智能，但错误退款审批 → 让 Agent 自己决定是否退款

退款条件清楚且涉及资金，不能把最终决定交给概率性输出。

正确的产品链路规则判硬条件 → 模型解释原因 → 人工处理边界案例

让确定性规则守最终动作，让模型做解释、归类和材料整理。

完整示范：自动退款先用规则守钱

现象：用户申请退款，团队想让模型读聊天记录后直接批准。

  1. 已知事实退款涉及金额、订单状态和明确政策。
  2. 第一个错误节点把最终资金动作交给模型判断。
  3. 正确动作规则检查硬条件，模型只总结原因和补充材料。
  4. 保持不变高风险动作由确定性系统决定，模型输出是候选辅助。
理解检查：退款审批第一步选什么

退款规则清楚，错误退款会造成资金损失。第一步应该怎么设计？

带着资料做一次：招聘助手怎么选方案

招聘助手要筛简历、解释匹配原因、安排面试。请区分哪些用规则，哪些用模型，哪些需要 Agent 调工具。

需要提示时展开

硬条件和权限适合规则；简历摘要和匹配理由适合模型候选；日程安排可能需要工具调用和人工确认。

方案已记录。

学历、城市、岗位权限等硬条件由规则或系统字段判断；模型生成简历摘要和匹配候选理由；Agent 只在候选通过规则后调用日历查空档，并在发出邀请前要求人工确认。

留下一个理解或疑问

方案决策记录怎么写，才不是“我觉得用 RAG”？

方案决策记录，也叫 Architecture Decision Record，简称 ADR。它不是长文档，而是把问题、约束、候选、取舍、验证和回滚写清楚。

0 / 2 步
白话解释

ADR 像一张可追责的选型单：为什么现在这样选，放弃了什么，之后用什么证据证明它对。

它不等于什么

它不是给技术方案贴一个名字，也不是只写最终结论。没有候选比较和验证计划，就不是可复盘的决策。

看起来像文档，但错误结论：使用 RAG，因为更准确

没有说准确指什么、和什么比、成本多少、失败怎么处理。

正确的产品链路问题 → 约束 → 候选 → 取舍 → 验证 → 回滚

把方案从口头偏好变成可评审、可测试、可迭代的记录。

完整示范：知识助手选 RAG先写候选比较

现象：团队说“用 RAG 做知识助手”，但没有说明为什么不只用 Prompt。

  1. 已知事实知识每周更新，答案必须标出处。
  2. 第一个错误节点只写技术名，没有写业务约束。
  3. 正确动作记录 Prompt-only、RAG、人工检索三个候选和取舍。
  4. 保持不变任何选型都要能回放到问题、约束和验证证据。
理解检查：ADR 最不能缺什么

团队只写了“采用 RAG，预计提升准确率”。最先要补哪一类信息？

带着资料做一次：写一条选型记录

选择一个 AI 产品场景，写出问题、候选、取舍、验证和回滚。

需要提示时展开

候选至少两个；验证不要写“用户满意”，要写能观察的效果、成本、延迟或错误类型。

方案已记录。

问题：客服需要回答每周更新的政策；候选：Prompt-only、RAG、人工检索；取舍：RAG 可标出处但有检索失败风险；验证：命中率、引用准确率、平均延迟、无法确认比例；回滚：检索失败时转人工或只返回制度入口。

留下一个理解或疑问

综合工作坊：修好一个“什么都上 AI”的学习助手方案。

这不是记忆测试。你可以回看任意模块、打开提示并修改方案。目标是把机制理解连接成一份能被评审的产品选型。

错误方案：学习助手所有问题都交给一个大模型；错题记录、课程状态和网页草稿都塞进 Prompt；政策和课程资料不做检索版本；复习提醒由 Agent 自己决定；文档只写“采用大模型提升学习效率”。

请改成：先判断事实位置，再选择 Prompt、检索增强、规则、Agent 或非 AI，并写出可验证的方案决策记录。
工作坊路线：不知道从哪里开始时按这五步走
  1. 任务学习助手到底要回答、推荐、评分还是安排动作？
  2. 事实答案依据在用户输入、正式状态、知识库还是外部系统？
  3. 机制哪些用 Prompt，哪些用检索，哪些由规则守住？
  4. 行动Agent 可以调用什么工具，哪些动作必须人工或程序确认？
  5. 记录用什么指标验证，失败后如何回滚或降级？
保存前核对：我的选型稿是否覆盖

W2 选型稿已保存。

网页只检查结构覆盖，不代替正式语义评分。现在可以对照示例，挑一处继续补强。

  1. 学习建议任务先读取正式状态、错题记录和用户目标；模型只生成候选建议。
  2. 课程资料和政策用检索增强，并校验版本、出处和适用范围。
  3. 复习到期、掌握状态和评测创建由规则与正式状态源决定。
  4. Agent 只能在用户确认后创建提醒或整理草稿，不能自行改写掌握状态。
  5. ADR 记录命中率、引用准确率、延迟、无法确认比例和回滚到人工复核的路径。
