Badcase 可以先理解为“能复现的质量失败记录”。它要带着输入、输出、版本、期望结果和影响范围进入修复队列，最后回到评测集里反复检查。

每个英文词都先回答“谁记录，谁复现，谁归因，谁修复，谁确认不再复发”。

Badcase 是不是一张用户投诉截图？

Badcase 可以先理解为“失败样本卡”。它要能让后来的人不问原用户，也能知道当时输入是什么、模型答了什么、为什么错、影响到谁。

0 / 2 步

Input

就是当时喂给系统的材料

包括用户问题、检索到的资料、上下文和配置。

能决定：是否可复现不能替代：期望答案

Output

就是系统实际给出的结果

要保存原文、引用、分数或动作，不只写“错了”。

能帮助：定位失败表现不能说明：根因是什么

Expected

就是用户或业务期望看到什么

要写清正确答案、正确动作或应该拒答的边界。

能帮助：判断失败类型不能直接决定：修复方案
白话解释

坏例卡像事故记录：谁遇到、哪一版、问了什么、答了什么、为什么不该这样答，都要留痕。

它不等于什么

“用户反馈不好用”不是坏例卡，因为无法复现，也无法进入修复和回归。

看起来有反馈，但错误截图 + 一句“模型答错”

缺少输入、版本和期望结果，后续没人能定位。

正确的产品链路用户现场 → 输入/输出/期望 → 版本配置 → 影响范围

先把失败变成可处理记录。

  1. 已知事实有错误输出，但缺少原问题、检索资料、模型版本和正确政策。
  2. 第一个错误节点只保存截图，无法判断是检索错、模型编造还是政策库过期。

  4. 保持不变坏例必须先可复现，才谈归因和修复。

留下一个理解或疑问

复现是不是重新问一遍同样的问题？

复现可以先理解为“尽量还原出错现场”。同一句问题不够，还要还原知识库版本、检索结果、prompt、模型版本、温度、用户状态和权限。

0 / 2 步
白话解释

复现像重播事故现场：输入一样只是开始，真正要确认的是整条系统链当时看到的材料是否一样。

它不等于什么

“我刚才问了一遍没错”不能说明问题已解决，因为你可能换了资料、模型或上下文。

看起来验证过，但错误复制用户问题 → 当前版本没复现 → 关闭

当前版本可能已经变了，原始检索和配置没有被还原。

正确的产品链路冻结现场 → 同版本复跑 → 记录是否稳定失败 → 再看当前版本

先确认原问题是否存在，再判断是否已被变化掩盖。

  1. 已知事实今天的知识库和模型配置可能不同。
  2. 第一个错误节点用当前现场替代出错现场。
  3. 正确动作用昨天的 index_version、prompt_version 和 retrieved_docs 复跑，并记录当前版本是否自然修复。
  4. 保持不变复现必须说明使用的是哪个现场版本。

留下一个理解或疑问

归因是不是默认归到模型能力不行？

归因可以先理解为“找到最该负责的系统层”。AI 产品出错可能来自模型生成、检索数据、规则定义、状态工程、权限、产品文案或评测标准，不能一概归到模型。

0 / 2 步
白话解释

归因像查水管哪里漏：水洒出来只是结果，要看是水源错、管道堵、阀门开错，还是用户被引导到错误入口。

它不等于什么

“模型幻觉了”不是完整归因。它可能没有拿到正确资料，也可能产品没有定义拒答边界。

看起来抓住核心，但错误输出错 → 模型差 → 换模型

跳过检索、数据、状态和规则检查，可能修错层。

正确的产品链路失败表现 → 责任层检查 → 根因证据 → 修复 owner

先用证据定位层级，再指定负责人。

完整示范：引用了过期政策先查资料链

现象：模型回答引用了去年政策，用户看到的是过期结论。

  1. 已知事实输出错，但引用确实来自知识库。
  2. 第一个错误节点直接责怪模型编造，忽略知识库时效。
  3. 正确动作归到数据更新或检索排序问题，再检查是否需要拒答过期资料。
  4. 保持不变根因要绑定证据和责任层，不用模糊标签替代。
理解检查：引用来自过期知识库

模型回答错误，但引用的材料确实是知识库里的过期文档。第一步该怎么归因？

坏例是不是按发现时间排队修？

优先级可以先理解为“先处理最伤业务和最可能复发的问题”。排序要看严重度、频率、用户影响、风险等级、是否阻断上线和是否有临时兜底。

白话解释

优先级像急诊分诊：不是谁先来谁先治，而是谁更危险、影响更多人、会不会继续扩大。

它不等于什么

“老板看到的先修”不是质量优先级；单个低风险文案错误也不应挤掉高风险退化。

看起来公平，但错误按提交时间顺序修

高风险坏例可能长时间暴露在线上。

正确的产品链路严重度 → 频率 → 业务影响 → 临时兜底 → 修复 SLA

先做分诊，再排修复。

完整示范：退款错答 vs 标点错误先看风险

现象：同一天收到一个退款政策错答和十个标点不统一反馈。

  1. 已知事实标点反馈更多，但退款错答会造成经济和信任风险。
  2. 第一个错误节点只按数量排序，把低风险高频问题放前面。
  3. 正确动作退款错答设为高优先级并临时降级或人工介入，标点归入批量优化。
  4. 保持不变优先级要看风险和影响，不只看出现次数。
理解检查：十个小问题和一个高风险问题

留下一个理解或疑问

修复是不是先改 prompt 看看？

修复可以先理解为“针对根因改对应系统层”。数据问题补资料或更新索引，检索问题调召回和重排，工程问题改状态和校验，规则问题改产品边界；prompt 只是其中一种手段。

白话解释

修复像对症下药：发烧可能是感染，也可能是中暑。没有归因就改 prompt，常常只是暂时掩盖症状。

它不等于什么

“加一句不要出错”不是可靠修复；如果数据过期或 Guard 缺失，prompt 无法稳定兜住。

看起来最快，但错误每个坏例都加 prompt 特例

正确的产品链路根因层 → 修复动作 → 验收样本 → 监控/回滚

修复要绑定 owner 和验证方法。

完整示范：资料没入库先补数据链
