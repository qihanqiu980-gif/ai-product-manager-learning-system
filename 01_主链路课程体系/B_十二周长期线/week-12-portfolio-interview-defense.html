留下一个理解或疑问

PRD 答辩是不是照着需求文档念一遍？

PRD 答辩可以先理解为“说明你为什么定义这个产品，而不是展示你会写文档”。要讲清用户问题、范围取舍、AI 参与点、非目标、成功指标和风险控制。

就是你如何界定问题

能证明：需求判断不能等于：一句口号

Scope Decision

就是做什么和不做什么

首版功能、延后功能和原因。

能证明：取舍能力不能隐藏：约束

Success Metric

就是怎样判断方案有效

激活、质量、成本、留存或效率指标。

能衡量：目标达成不能伪造：真实数据
白话解释

PRD 像产品决策书，不是格式模板。答辩时要让对方听懂：你为什么选这个问题、为什么不做另一个方案、首版怎样验证、失败时怎么知道。

它不等于什么

它不等于功能列表、页面说明或“用户可以点击什么”。AI 产品 PRD 还必须说明模型在哪参与，确定性程序守哪些边界。

架构图是不是把所有技术组件画出来就行？

架构答辩可以先理解为“说明每层负责什么、边界在哪里、失败怎么恢复”。AI 产品架构重点不是组件多，而是前端、服务端、模型、检索、校验、状态和证据各自不越权。

Responsibility Boundary

就是每层负责和不负责什么

能证明：边界意识不能模糊：最终写入权

Data Flow

就是数据怎样从输入走到结果

输入、检索、生成、校验、保存、展示。

能帮助：排错不能遗漏：失败路径

Control Point

就是必须被程序守住的关口

能降低：风险不能交给：模型自觉
白话解释

架构图像机场流程图。不是把所有柜台都画出来，而是说明旅客从哪里进入、谁查证件、谁托运行李、哪里安检、出问题怎么退回。AI 架构要把“模型建议”和“产品动作”分开。

它不等于什么

它不等于技术名词拼图，也不等于把模型放在中心。不能让面试官听完还不知道 Key 在哪里、状态谁决定、证据如何回放。

看起来合理，但错误Frontend + LLM + Database + Vector DB

正确的产品链路用户输入 → 服务端代理 → RAG/模型候选 → 校验/Guard → 状态/报告

用数据流和控制点解释架构。

留下一个理解或疑问

评测、风险和商业是不是答辩时分别补几页？

评测、风险和商业可以先理解为“同一个产品判断的三类证据”。评测说明效果有没有达标，风险说明什么不能做或要拦截，商业说明价值是否大于成本。它们要连在一起，而不是三份孤立附件。

0 / 2 步

Quality Evidence

就是效果是否可接受的证据

Eval set、Rubric、badcase、回归结果。

能证明：质量判断不能证明：商业可行

Risk Evidence

就是边界是否被守住的证据

隐私、越权、无证据回答、拒答降级。

能证明：可控性不能消除：全部风险

Business Evidence

就是价值和成本是否说得通

激活、留存、付费点、单位成本和路由。

能证明：产品可持续假设不能伪造：真实营收
白话解释

这三类证据像体检报告、保险条款和账本。只说效果好不够，还要说哪里不能乱答、一次任务成本是否可承受。面试时要展示你能把质量、风险和商业放在一个决策里。

它不等于什么

它不等于分别贴一页 Eval、一页风险、一页商业化。也不能用页面练习结果伪装成真实生产指标。

看起来合理，但错误准确率 85% → 产品可上线

没有看高风险 badcase、拒答边界、成本和用户价值。

正确的产品链路质量指标 → 风险护栏 → 单位成本 → 发布决策

  4. 保持不变AI 产品发布判断要同时看质量、风险和商业证据。

岗位匹配是不是把 JD 关键词塞进简历？

JD 能力映射可以先理解为“把岗位要求翻译成你的项目证据”。目标不是堆关键词，而是让每个关键词背后都有可追问的项目事实、取舍和结果。

Capability Signal

就是岗位想看到的能力信号

Gap Handling

每个能力点都能落到可核验经历。

留下一个理解或疑问

项目答辩是不是背熟一段自我介绍就够？

项目答辩可以先理解为“在追问中保持证据、边界和取舍一致”。面试官不会只听顺稿，会问为什么不这么做、数据怎么来、失败怎么办、你的贡献是什么。

Core Claim

就是你最想证明的一句话

例如我能把 AI 能力落成可评测产品闭环。

能稳定：答辩主线不能夸大：未验证结果

Question Tree

就是围绕项目可能被追问的问题树

Why、How、Evidence、Risk、Trade-off、Next。

能帮助：抗追问不能替代：真实理解

Boundary Answer

就是遇到未做事项时的回答方式

承认证据范围，说明假设和下一步验证。

能体现：可信度不能变成：找借口
白话解释

答辩不是朗读，而是压力测试。你需要知道每个结论的证据在哪里、哪些没有验证、为什么这样取舍。如果被问到没做过的部分，要守住边界，而不是临场编成果。

它不等于什么

它不等于背稿，也不等于把所有问题都答得很满。AI 产品答辩尤其不能把 demo、草稿或假设说成真实上线成果。

看起来合理，但错误背一段完整介绍 → 遇到追问临场发挥

一旦问到数据来源、模型边界或失败案例，就容易前后不一致。

正确的产品链路核心主张 → 证据位置 → 追问树 → 边界回答 → 下一步

用结构抗追问。

完整示范：被问“为什么不用更强模型”先回到取舍

现象：面试官问为什么不全用最强模型，候选人回答“因为成本高”，但说不出成本口径和质量门槛。

  1. 已知事实项目中有模型路由、单位成本和质量护栏方案。
  2. 第一个错误节点只给结论，没有证据链。
  3. 正确动作回答任务分层、质量门槛、单位成本、风险和灰度实验，再说明什么条件下会升级强模型。
  4. 保持不变答辩追问要回到证据、取舍和边界。
