先在脑中搭起一张图：评测不是临时问模型几道题。

产品评测可以先理解为“用固定样本、固定标准和固定记录方式，比较不同版本”。它不是找几个顺眼案例看输出，而是先规定真实任务、正确答案、评审规则和上线门槛。

先讲判断动作，再讲术语

每个英文词都先回答“谁选样本，谁确认答案，谁评审，谁决定上线”。

用错误评测划边界

不把 demo 成功当效果提升，而是找到第一个会让结论失真的环节。

带着场景写评测方案

可以回看提示和示例，目标是写出可复测、可比较、可汇报的评测设计。

Eval Set测哪些题

负责覆盖真实任务、边界样本、失败样本和高频用户需求。

→
Golden Set什么算对

负责保存人工确认的标准答案、引用依据和评分标准。

→
Review谁来评

负责人工一致性、Judge 辅助筛查和争议仲裁。

→
Report是否上线

负责版本对比、失败分层、风险说明和回归决定。

选样本定金标跑基线控一致写决策

Eval Set 是不是随便挑几条典型例子？

Eval Set 可以先理解为“固定考卷”。它要覆盖真实用户任务、常见边界和已知坏例子，而不是只放团队最容易演示成功的样本。

0 / 2 步

Task

就是用户要完成的事

例如查政策、改文案、判断资料是否齐全。

能决定：样本来自哪类真实任务不能决定：模型是否答对

Slice

就是分层抽样

把高频、低频、边界、失败、风险样本分开看。

能帮助：发现哪类任务退化不能替代：金标答案

Holdout

就是不能被调参看穿的保留题

避免团队反复根据同一批题调 prompt 后虚假变好。

能阻止：过拟合样本不能证明：全量用户场景都安全
白话解释

评测集像固定考卷：题目要代表真实工作，还要保留难题和旧失败题，方便下个版本复测。

它不等于什么

20 条手挑的漂亮 demo 不是 Eval Set，因为它无法暴露长尾、边界和退化。

看起来省时，但错误挑 20 条容易成功的例子 → 看平均分

样本偏向成功，报告会高估真实效果。

正确的产品链路真实任务 → 样本分层 → 边界/失败样本 → 固定版本

先定义覆盖面，再让版本接受同一批样本检验。

完整示范：政策问答助手先补样本覆盖

现象：团队只用 20 条热门政策问答评测，新版本全对。

  1. 已知事实热门题能说明高频场景，但没有覆盖过期政策、相似政策和无答案问题。
  2. 第一个错误节点把 demo 样本当成完整评测集。
  3. 正确动作按任务和风险分层，加入边界题、坏例题和无答案题。
  4. 保持不变评测集必须代表产品要承诺的任务范围。

留下一个理解或疑问

Golden Set 是不是让当前模型生成一批标准答案？

Golden Set 可以先理解为“人工确认过的标准答案和评分依据”。它不能由同一个待测模型自己生成再自己通过，否则评测会变成自我证明。

0 / 2 步
白话解释

金标像考卷答案和判分依据：需要人或可信资料确认，写清什么必须出现、什么不能编、哪些答案也可接受。

它不等于什么

模型写得很流畅的参考答案不是金标，除非经过人工核对、引用来源和版本锁定。

看起来自动化，但错误待测模型 → 生成答案 → 再按该答案评分

模型偏好会被写进标准答案，评测失去独立性。

正确的产品链路可信资料/专家 → 金标答案 → 可接受变体 → 评分规则

先让标准答案独立于待测模型。

完整示范：招聘匹配解释先锁定金标来源

现象：当前模型生成“候选人适合高级产品经理”，团队把这段话当标准答案。

  1. 已知事实答案没有人工确认，也没有绑定 JD 和简历原文。
  2. 第一个错误节点待测模型正在定义自己要通过的标准。
  3. 正确动作由评审根据 JD 必要条件和简历证据写金标，并列出可接受表达。
  4. 保持不变金标要独立、可追溯、可版本管理。
理解检查：谁来写金标

团队想让待测模型先生成标准答案，再用 Judge 判断新输出是否接近。第一步应该怎么处理？

留下一个理解或疑问

新模型分数高，是不是就说明产品变好了？

Baseline 可以先理解为“当前版本或简单方案的参照线”。没有基线，就不知道提升来自新模型、样本偏差、提示变化，还是评测口径变松。

0 / 2 步
白话解释

基线像体检前的旧指标：新版本必须和同一批样本、同一套标准下的旧版本比较。

它不等于什么

只看新模型一次平均分不是基线比较；换了样本或评分规则也不能直接说提升。

看起来进步，但错误新模型 86 分 → 旧模型未知 → 宣布提升

没有参照，无法证明比当前系统更好。

正确的产品链路旧版本/规则方案 → 同一评测集 → 同一金标 → 差异分析

先让旧版本跑出基线，再比较新版本。

完整示范：文案改写助手先跑旧版本

现象：新模型在 100 条样本上平均 4.2 分，团队准备上线。

  1. 已知事实新模型分数存在，但旧版本、规则模板和人工参考都没跑。
  2. 第一个错误节点把绝对分数当成版本提升。
  3. 正确动作用同一评测集跑当前线上版本和新版本，按任务分层比较。
  4. 保持不变上线判断要看相对提升、退化样本和风险门槛。
理解检查：缺基线时先做什么

新模型在评测集上平均 86 分，但旧版本没有跑过这批样本。第一步应该怎么做？

需要提示时展开

基线应包含当前线上模型、简单规则/模板方案和必要的人工参考。新旧版本使用同一 Eval Set、同一 Golden Set、同一评分规则，报告整体分、关键分层分、成本、延迟和退化样本；高风险 slice 退化即不得全量上线。

留下一个理解或疑问

人工评测是不是找一个同事看一遍就够？

人工评测的关键不是“有人看过”，而是评审规则清楚、多人结果能对齐、争议能仲裁。否则评测报告只是某个人的主观感受。

0 / 2 步
白话解释

人工评测像阅卷：要有判分规则、样例校准、双人复核和争议处理，才能稳定判断模型输出。

它不等于什么

“PM 看着还不错”不是人工评测，因为没有一致性，也无法解释分歧。

看起来有人把关，但错误一个评审自由打分 → 平均分

不同评审理解不一致，分数不可比较。

正确的产品链路标注规则 → 校准样例 → 双人评审 → 一致性检查 → 仲裁

先让人按同一把尺子评，再汇总结果。

完整示范：医疗问答安全性先校准评审

现象：同一条回答，A 评审判可用，B 评审判高风险。

  1. 已知事实两个评审结果冲突，说明规则或样例校准不足。
  2. 第一个错误节点直接取平均会掩盖安全争议。
  3. 正确动作回到标注规则，明确高风险定义，安排仲裁并更新示例。
  4. 保持不变高风险任务必须保留人工一致性和争议记录。
理解检查：评审不一致怎么办

两个评审对同一输出给出相反结论。第一步应该怎么处理？

留下一个理解或疑问

LLM-as-a-Judge 能不能直接替代人工评审？

LLM-as-a-Judge 可以先理解为“让另一个模型按规则做候选评审”。它适合扩大筛查、生成理由和发现可疑样本，但不能替代金标、人工仲裁和高风险上线判断。

0 / 2 步
白话解释

Judge 像助教批改：速度快、能给理由，但仍要被抽检、校准和版本管理。

它不等于什么

换一个模型打分不等于真相。Judge prompt、模型版本、温度和评分规则一变，结果就可能变。

看起来自动闭环，但错误待测模型输出 → Judge 打分 → 自动上线

两个模型可能共享偏差，且没有金标和人工边界。

正确的产品链路金标/Rubric → Judge 候选评分 → 人工抽检/仲裁 → 版本锁定

Judge 是评审工具，不是最终事实源。

完整示范：Judge 偏爱长答案先做校准

现象：Judge 总给长答案更高分，即使短答案更准确。

  1. 已知事实Judge 评分和金标不一致，偏向表达长度。
  2. 第一个错误节点把 Judge 分数当最终裁决。
  3. 正确动作用金标样本校准 Judge prompt，记录版本，并对高风险分歧人工复核。
  4. 保持不变Judge 结果必须被金标和人工抽检约束。
理解检查：Judge 分数能不能直接上线

Judge 给新模型显著高分，但人工抽检发现它偏爱更长答案。第一步应该怎么处理？

留下一个理解或疑问

评测报告为什么不能只写平均分提升？

评测报告要让产品、研发和业务知道：哪个版本在哪些任务上变好，哪些地方退化，样本和标准是否可信，是否满足上线门槛。平均分只是入口，不是决策。

0 / 2 步
白话解释

报告像上线前的体检单：不仅写总分，还要写分层结果、badcase、成本延迟、风险和建议动作。

它不等于什么

“平均分 +8%”不能单独支持上线，因为高风险任务可能退化，Judge 版本也可能变了。

看起来增长，但错误平均分上涨 → 全量上线

隐藏分层退化和高风险失败，会让产品决策失真。

正确的产品链路总体指标 → 分层指标 → badcase → 风险门槛 → 上线/灰度/回滚

报告必须回答下一步动作。

完整示范：总分涨但风险退化先看分层

现象：客服助手平均正确率从 78% 到 84%，但退款争议类从 70% 降到 52%。

  1. 已知事实总体提升存在，但高风险 slice 明显退化。
  2. 第一个错误节点只看平均分会忽略关键业务风险。
  3. 正确动作报告标记不得全量上线，安排退款争议类修复和回归。
  4. 保持不变评测报告要支持决策，不只展示好看的数字。
理解检查：总分提升但高风险退化

新版本平均分提升，但高风险退款争议类明显下降。第一步应该怎么处理？
