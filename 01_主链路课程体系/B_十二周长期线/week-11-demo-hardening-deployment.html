0 / 2 步

Feature Promise

就是你对演示用户承诺能完成的事

例如只支持单文档制度问答，返回带引用答案。

能决定：测试范围不能扩成：所有知识库需求

Out of Scope

就是这版明确不做的事

例如多租户权限、批量导入、实时协作暂不支持。

能减少：演示翻车不能隐藏：真实限制

Acceptance Path

就是验收时必须跑通的路径

写清输入、操作、期望输出和失败提示。

能证明：首版稳定不能替代：正式生产监控
白话解释

功能范围像餐厅菜单。菜单上写了什么，就要稳定出什么；没写的菜不能临时承诺。Demo 首版要让用户相信你能交付一条清楚路径，而不是看到一堆半成品入口。

它不等于什么

它不等于功能越多越成熟，也不等于把入口藏起来就算没有问题。边界要被明确写出来，让演示、测试和回归都按同一份承诺走。

看起来合理，但错误能想到的入口都加上

入口越多，未完成状态、权限缺口和测试遗漏越多。

正确的产品链路承诺功能 → 不做范围 → 验收路径 → 回归用例

留下一个理解或疑问

边界状态是不是只写一个“出错了”？

边界状态可以先理解为“用户走不下去时，产品仍然告诉他发生了什么、能做什么、不能做什么”。它覆盖空数据、权限不足、资料不足、服务繁忙、超出额度和输入不支持。

0 / 2 步

Empty State

就是还没有可用内容时的状态

例如没有上传文档、没有历史问题。

能引导：下一步输入不能伪装：已有结果

Blocked State

就是系统拒绝继续时的状态

例如权限不足、超出额度、文件类型不支持。

能保护：边界和成本不能只说：失败

Recoverable State

就是用户还能补救的状态

例如资料不足、模型超时、网络失败。

能提供：重试或补充材料不能丢失：原输入
白话解释

边界状态像路牌。路不通时，路牌要说清楚是封路、没权限、资料不够，还是可以绕行。AI 产品更要避免用一个模糊错误遮住不同事实。

它不等于什么

它不等于统一弹窗“请求失败”，也不等于把用户送回首页。不同边界代表不同责任和下一步，必须分开处理。

看起来合理，但错误任何异常 → 出错了，请稍后再试

用户不知道是自己缺材料、没有权限、服务慢，还是产品不支持。

正确的产品链路边界类型 → 原因说明 → 可行动下一步 → 保留输入

让用户和评审者都能看见产品如何处理真实限制。

完整示范：资料不足不是系统错误先区分边界类型

现象：用户问“新员工试用期报销规则”，知识库只包含年假制度。页面显示“系统异常”。

  1. 已知事实系统正常，检索也正常，只是资料没有命中问题。
  2. 第一个错误节点把证据不足包装成系统故障。
  3. 正确动作显示资料不足，展示已检索来源，提示补充试用期或报销制度。
  4. 保持不变边界状态要说明真实原因和下一步，不能用模糊失败替代。

AI 很慢的时候，只加一个 loading 动画够吗？

响应时间管理可以先理解为“让用户知道请求到了哪一步、最多等多久、等不下去时怎么办”。AI Demo 可能慢在上传、检索、模型、校验或网络，每一段都需要可解释。

0 / 2 步

Latency Budget

就是每个阶段最多花多久

例如检索 2 秒、模型 8 秒、总等待 15 秒。

能约束：体验和成本不能保证：外部服务永远快

Progressive Feedback

就是逐步告诉用户正在做什么

例如正在找资料、正在生成、正在校验证据。

能降低：不确定感不能伪造：实际进度

Timeout Exit

就是超时后的出口

停止等待，保留输入，提供重试、稍后查看或降级结果。

能保护：体验不能无限转圈
白话解释

Loading 动画像“请稍候”的牌子，但用户还需要知道排队多久、卡在哪、能不能离开。AI 产品必须把长等待拆成阶段，并设置明确停止条件。

它不等于什么

它不等于把 spinner 做漂亮，也不等于无上限等待模型。没有阶段、没有超时、没有保留输入的 loading 只是把失败拖长。

看起来合理，但错误点击生成 → 一直转圈

用户不知道请求是否提交、能不能刷新、是否会重复扣费。

正确的产品链路阶段提示 → 超时上限 → 保留 request_id → 重试/稍后/降级

慢请求也能被解释和恢复。

完整示范：模型生成超过 20 秒先设置停止条件

现象：面试反馈生成一直转圈，用户重复点击三次，产生三次模型调用。

  1. 已知事实请求已经提交，缺少按钮锁定、阶段提示和 request_id。
  2. 第一个错误节点把等待体验交给无限 spinner。
  3. 正确动作提交后禁用重复按钮，显示阶段和预计上限；超时后保留 request_id，允许同一请求重试或稍后查看。
  4. 保持不变任何慢 AI 请求都要有阶段反馈、超时上限和幂等恢复。

成本护栏可以先理解为“让每次演示调用都在可承受范围内”。AI Demo 即使不是生产，也要控制文件大小、检索次数、模型档位、重试上限、缓存和调用额度。

0 / 2 步

Cost Budget

就是一次任务最多花多少钱或多少资源

按用户任务，而不是单次 API 调用来估算。

能限制：失控调用不能证明：商业可行

Rate Limit

就是单位时间或用户可调用次数

防止重复点击、脚本刷接口或演示现场误用。

能保护：成本不能替代：权限

Model Tier

就是不同任务使用不同模型档位

低风险轻任务用便宜模型，高价值输出才用强模型。

能平衡：质量和成本不能忽略：质量门槛
白话解释

成本护栏像演示用电闸。你不一定要算清长期商业模型，但至少要知道一次演示最多调用几次、失败重试几次、文件多大、什么时候停止。

它不等于什么

它不等于上线后再看账单，也不等于为了省钱全用最差模型。成本控制要和质量、风险、演示稳定性一起看。

看起来合理，但错误免费输入任意大文件 + 无限重试 + 强模型全量

一次演示就可能产生高成本和长等待，还难以复现。

正确的产品链路任务预算 → 输入限制 → 路由档位 → 重试上限 → 成本日志

让演示调用可控，也让后续优化有依据。

移动端和无障碍是不是最后美化时再看？

移动端与无障碍可以先理解为“不同设备和不同操作方式都能完成核心路径”。W11 的重点不是装饰，而是表单可填、按钮可点、文字可读、键盘可走、反馈不只靠颜色。

0 / 2 步

Responsive Flow

就是核心路径在小屏也能走完

输入、上传、结果、错误和引用都不能横向溢出。

能保护：移动演示不能只测：桌面

Keyboard Path

就是不用鼠标也能操作

Tab 顺序、焦点、按钮和表单都清楚。

能支持：键盘和辅助技术不能依赖：悬停

Accessible Feedback

就是反馈能被读懂和读出

错误、成功、loading 要有文本和 aria-live。

能减少：误解不能只靠：颜色
白话解释

移动端和无障碍不是给页面加一层善意标签，而是保证核心任务真的能完成。面试官用手机打开、用户只用键盘操作、屏幕阅读器读状态时，产品都不能断。

它不等于什么

它不等于字体缩小、内容横滑、按钮堆在一起，也不等于只要颜色对比看起来还行。核心流程必须被实际走一遍。

看起来合理，但错误桌面可用 → 移动端自然可用

长表单、表格、引用和按钮在小屏可能溢出或遮挡。

正确的产品链路核心路径 → 小屏检查 → 键盘检查 → 文本反馈 → 修复回归

用真实操作验证，而不是只看截图。

  2. 第一个错误节点只在桌面检查视觉完整。
  3. 正确动作修复响应式宽度、按钮换行和错误文本；用键盘和小屏重新走完整路径。
  4. 保持不变核心任务必须在目标设备和辅助操作方式下都能完成。
