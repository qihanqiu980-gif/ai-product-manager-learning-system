Browser、Server Proxy、Provider Adapter 到底分别是什么？

先别急着记 Provider Adapter。先从你正在使用的网页开始，一层层看请求往哪里走、每层能看到什么、为什么模型密钥必须停在服务端。

0 / 2 步

Browser

就是用户电脑或手机里的浏览器页面

它负责收集输入、发送业务请求、展示结果。页面代码会下载到用户设备，所以任何写进前端的 Key 都可能被看到。

能看见：用户输入、页面状态、服务端返回结果不能拥有：模型 API Key、最终业务写入权

Server Proxy

就是你自己的后端接待台

浏览器先把业务请求交给它。它核对登录、session、权限和字段，再决定是否调用模型，并把结果整理后返回页面。

能看见：会话、权限、允许的业务字段负责：守密钥、记日志白名单、执行 Guard

Provider Adapter

就是服务端里的“模型供应商翻译器”

业务代码只说“分析这段回答”，Adapter 再把它翻译成 OpenAI、Claude 或其他供应商各自需要的请求格式。

能看见：统一模型请求、供应商响应、环境变量中的 Key负责：认证、格式转换、错误归一化、mock / live 切换
白话解释

不要让每个页面自己认识不同模型 API。统一由服务端适配层处理供应商差异，业务流程只接收一种经过整理的候选格式。

它不等于什么

它不是一段更复杂的 Prompt，也不是让模型获得业务写入权。它首先是一道服务端信任边界。

看起来省事，但错误Browser → 模型供应商

前端直接带 Key 调模型。即使使用 HTTPS，用户仍能在页面代码、网络面板或调试工具里读到 Key。

正确的产品链路Browser → Server Proxy → Provider Adapter → 模型供应商

Browser 只发送业务字段；自己的服务端持有秘密并先做权限、状态和输入检查。

完整示范：AI 面试系统先看判断过程

错误方案：研发把 MODEL_API_KEY 放进前端构建变量，让浏览器直接调用模型。

  1. 已知事实前端资源会被下载，构建变量不能保护秘密。
  2. 第一个错误节点密钥进入 Browser，信任边界已经被穿透。
  3. 正确动作停止调用并轮换密钥；浏览器改为调用 Server Proxy。
  4. 保持不变换成客服或销售助手，密钥仍只能由服务端读取。
理解检查：HTTPS 能不能保护前端里的 Key？

AI 客服页面准备上线，工程师提议把 Key 放进请求体，并承诺“HTTPS 会保护它”。第一步应该做什么？答错也会直接看到完整解释，可以修改后再试。

模型为什么只能给“候选”，不能直接批准业务动作？

严格 JSON 只证明机器能够读懂这份输出，不证明其中的价格、引用、权限或状态是真的。这个模块要建立“模型提建议，程序做裁决”的边界。

0 / 2 步
白话解释

模型像提交方案的实习生；Validator 像审核人。实习生可以写候选分数和追问，但审核人必须逐项检查后才决定是否采用。

它不等于什么

strict: true 不等于业务正确。Schema 也不能验证引用是否真的来自当前回答，更不能替代权限和状态 Guard。

完整示范：模型返回 next_state识别越权字段

候选输出：结构完全合法，同时包含 next_state: "completed"，但当前还剩两道基础题。

  1. 已知事实JSON 可解析；业务题目尚未完成。
  2. 第一个错误节点模型候选试图决定 session 状态。
  3. 正确动作忽略越权字段，校验允许字段，由程序读取题目队列并决定下一步。
  4. 保持不变所有产品中，模型输出都只能是候选，不能拥有最终写入权。
理解检查：JSON 合法之后还缺什么

模型返回合法结构：分数为 3，引用文本却没有出现在用户原回答中，同时建议直接完成 session。答完会显示每一步校验为什么存在。

带着资料做一次：销售话术助手的校验链

模型生成一段候选报价话术，并给出 approved=true。请区分哪些内容可以作为候选，哪些事实必须由程序或业务系统核对。

需要提示时展开

把字段分成三篮：模型可生成的内容、程序可校验的格式、业务系统才知道的事实与权限。

方案已记录。先核对自己是否把“候选内容”和“业务批准”分开。

可以保留候选话术、摘要和风险提示；价格、折扣权限、客户事实与 approved 状态必须来自业务系统和确定性规则。候选通过类型、范围和事实校验后，程序才决定展示、重写或阻断。

不用重新背定义。记录“结构正确”和“业务正确”之间你现在能分清的一点，或仍然模糊的地方。

模型调用失败时，为什么不能一直重试到成功？

超时、429、网络、空输出和 Schema 失败看起来都像“再试一次”就行，但真实产品还要控制重复扣费、重复写入、等待时间和用户原始数据。

0 / 2 步
白话解释

重试像重新刷一次门禁，不是一直撞门。系统必须知道已经试了几次、是否可能重复写入、什么时候停止并走备用路线。

它不等于什么

安全降级不等于假装成功，也不等于清空用户输入。它要保留事实、披露限制，并阻止无证据分数或追问。

完整示范：连续 429先保住原业务请求

现象：第一次调用返回 429，一次修复性重试仍失败。用户回答已经在服务端收到。

  1. 已知事实Provider 不可用，不代表用户回答无效。
  2. 第一个错误节点继续无限重试会放大成本、延迟和重复副作用。
  3. 正确动作停止调用，保留 answer 与 request_id；写入 score=null 的降级对象。
  4. 保持不变换任何业务，都要固定重试上限并设计可恢复的降级状态。
理解检查：达到重试上限后怎么办

面试回答已提交，模型连续超时并达到一次重试上限。页面还可以继续完成剩余基础题。

带着资料做一次：OCR 超时后的恢复链

用户已经上传报销凭证，OCR 模型持续超时。请设计一条不会重复扣费、不会丢文件、也不会伪造识别结果的恢复链。

需要提示时展开

依次回答五件事：保留什么、用什么稳定身份重试、最多几次、失败后页面显示什么、用户怎样从原 session 恢复。

方案已记录。检查恢复链是否同时处理了成本、幂等、原始输入和结果诚实性。

保留原文件、session_id 与稳定 request_id；只做固定次数重试；达到上限后停止 OCR 调用，状态标记为待人工确认或部分可用，不生成虚假字段，并允许用户稍后从同一 session 恢复。

Guard 是什么？为什么模型说“下一步”不代表产品就能执行？

Guard 可以理解为动作发生前的门卫规则：它核对当前题、权限、次数、request_id 和 session 状态，条件不满足就阻止动作。

0 / 2 步
白话解释

模型像提出“我还想问一句”的面试官，Guard 像流程主持人：它要确认时间、题目和次数都允许，才把问题交给用户。

它不等于什么

follow_up.needed=true 不是动作命令。追问候选仍要服从状态机，模型也不能自行宣布 session 完成。

完整示范：追问额度已用完候选不自动变成页面动作

现象：模型提出一个有价值的追问，但当前题已经使用过唯一追问额度。

  1. 已知事实候选追问相关；follow_ups_used 已等于 max_follow_ups。
  2. 第一个错误节点若直接展示，会违反确定性停止条件。
  3. 正确动作阻断追问，由程序选择下一基础题或完成流程。
  4. 保持不变所有动态生成动作都必须经过业务额度、权限和状态 Guard。
理解检查：旧题的追问还能不能展示

模型建议追问，但请求携带的是旧 question_id；当前 session 已经进入下一道基础题。

模型只能生成“进入赔付决定”的候选；Server Proxy 依据缺失材料和当前 session 执行 Guard，阻断该动作。session 保持 collecting_documents，页面继续投影补充材料状态，不能靠地址或候选字段反向改写业务事实。

Grounded Report 是什么？为什么“总结得合理”仍然不够？

Grounded 的意思是“有可回放的依据”。每个非空分数和 claim 都要能回到 question_id、answer_id 和逐字 quote；没有证据时必须明确保留空值和限制。

0 / 2 步
白话解释

最终报告像一份可复核的评审记录：读者不仅看到结论，还能点回原问题、原回答和支撑结论的那句话。

它不等于什么

语义相近的改写、模型自信度和流畅摘要都不能替代逐字证据。“没有观察到”也不能写成“用户没有能力”。

完整示范：摘要多说了一个结论让报告停在证据边界

原回答：“我会先核对服务端 session，再决定是否重试。”模型摘要却写成“用户完整掌握幂等与恢复”。

  1. 已知事实原话支持服务端事实优先，不完整支持“掌握幂等”。
  2. 第一个错误节点claim 超出了逐字 quote 的范围。
  3. 正确动作缩小 claim 或令对应 score=null；报告标记 partial 并写入 limitation。
  4. 保持不变换任何评审场景，结论范围都不能超过可回放证据。
理解检查：没有逐字引用时如何发布

模型给出高质量摘要和 3 分，但 evidence_quote 只是对用户回答的合理改写，不是逐字子串。
