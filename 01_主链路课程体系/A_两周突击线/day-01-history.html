一张能指导工作的知识地图，不是术语清单。它让每个节点都回答一个产品问题：用户为什么需要它、AI 是否必要、哪些职责交给模型或程序、如何证明质量、风险何时升级、每次会话是否可负担，以及上线后是否真的带来用户与商业结果。

AI 产品经理不训练模型、不写接口，为什么仍要对结果负责？

AI 产品经理负责把用户与业务问题变成可落地、可验收、可兜底的产品决定：定义目标、方案、体验、评测、权限、上线门槛与结果。算法和研发负责专业实现，但不能替产品决定“什么结果对用户有价值、什么风险不可接受”。

0 / 2 步
白话解释

产品经理像总导演：不亲自拍每个镜头，也不替灯光师接线，但要决定故事给谁看、怎样算成功、哪些内容不能播，以及任何关键岗位是否真的有人负责。

它不等于什么

产品责任不等于亲自训练模型、部署服务或出具法律结论；也不等于把模型效果、风险和用户结果全部交给算法团队。职责边界是清楚分工，不是甩开结果。

AI 产品经理定义价值、标准、权限与门槛

看用户、业务、质量、风险、成本和结果；不得用“技术已实现”替代产品验收。

算法 / 数据实现和优化模型能力

负责数据、模型、实验和技术评估；不独自决定用户体验、业务容忍度或上线权限。

研发 / 工程实现系统控制与可靠交付

负责接口、状态、权限、日志、恢复和性能；不替产品定义核心假设与成功结果。

业务 / 法务 / 运营提供领域规则与风险审核

确认业务事实、合规边界和人工流程；不能把所有例外都留给上线后处理。

两种甩锅“产品只提需求” / “产品必须亲自训练模型”

前者放弃结果责任，后者混淆专业分工；都会让真正的质量、权限和风险决定无人负责。

正确分工产品定义 what / why / gate → 专业团队实现 how → 产品按证据验收

每项关键决定都有负责人、输入证据、通过条件和失败动作。

完整示范：AI 面试教练编造候选人经历产品边界不是一句“优化模型”

现象：模型在反馈中加入用户未说过的业绩数据。算法可以优化 Prompt 或模型，研发可以增加原文比对，产品仍要决定哪些错误必须阻断、怎样提示用户、何时人工介入和是否允许上线。

  1. 已知事实错误影响反馈可信度；用户原回答可作为核对来源，严重度与发生范围可以被评测。
  2. 第一个错误节点若产品只把问题写成“请算法提高准确率”，就没有定义什么算编造、如何拦截和达到什么门槛才可上线。
  3. 正确动作产品定义引用必须来自原文、严重错误率门槛、拒答与人工路径；算法和研发实现，产品用固定用例验收并决定放行。
  4. 保持不变产品不替代专业实现，但要保证用户价值、证据标准、权限、兜底和业务结果都有清晰决定。

需要提示时展开
  • 产品要定义用户、价值、评测、权限、风险和结果指标。
  • 算法与研发分别负责模型与系统实现，但不能自己决定所有门槛。
  • 招聘决策影响个人权益，高风险结论需要人工和合规边界。

职责图已记录。检查是否既没有甩锅，也没有替代专业团队。

产品定义仅做材料整理与候选风险提示，不自动淘汰；设证据必须来自简历、误伤率、公平性、人工复核和试点门槛。算法负责提取与排序实验，研发负责权限、日志、来源核对、状态和回退，招聘业务确认岗位标准并人工作出用人决定，法务审核隐私与歧视风险。证据缺失或冲突时输出“不足以判断”；产品基于跨团队证据决定是否扩大试点。

为什么一张知识地图不能从“选模型”开始，也不能在“上线”结束？

AI 产品经理知识地图是一条连续的决策链。它先证明用户与业务问题，再定义目标、AI 必要性和方案；中间用评测、Badcase、风险与成本限制上线；最后用真实用户行为和商业结果判断产品是否成立。

0 / 2 步
白话解释

它像飞行路线图：不只画起飞和落地，还要标出目的地、燃料、天气、检查点和备降机场。每个节点缺失，后面的“顺利飞行”都可能只是错方向。

它不等于什么

知识地图不是课程目录、技术架构图或功能清单。它必须让团队知道每一阶段要回答什么问题、看什么证据、不达标时回到哪里。

1用户与业务问题

谁在什么场景遇到什么可验证痛点？

2目标与核心假设

希望改变什么行为或结果？为什么值得验证？

3AI 必要性

哪些子任务需要语义理解或生成，哪些不需要？

4方案与职责

非 AI、规则和 AI 怎样组合，各自不能决定什么？

5产品与系统实现

输入、上下文、状态、权限、输出和恢复怎样工作？

6评测与 Badcase

正常、边界和失败用例怎样证明质量与回归？

7风险与成本门槛

何时追问、拒答、人工、停止放量？每次使用是否可负担？

8MVP 上线实验

最小闭环怎样在受控范围验证核心假设？

9用户与商业结果

价值、转化、留存、成本和单位经济是否成立？

功能链模型选择 → Prompt → 页面 → 上线

只能说明做了什么，不能说明为什么需要、怎样验收、风险是否可控以及商业上是否值得继续。

决策链problem / hypothesis → necessity / solution → evidence / gate → experiment / result

每一段都有输入事实、产品决定、验证指标和不达标动作。

完整示范：AI 面试教练知识地图上线不是终点

方向：帮助转岗学习者完成个性化面试练习。团队不能只证明“模型能生成问题”，还要证明问题相关、追问合理、反馈有证据、风险可控、会话成本可承受，且用户愿意完成并再次使用。

  1. 已知事实用户需要针对自身经历练习；模型有生成优势，也可能编造；完整会话涉及状态、评测、风险和成本。
  2. 第一个错误节点若从模型选择开始，团队还没证明用户问题和 AI 必要性；若在上线结束，也没证明用户价值和单位经济。
  3. 正确动作按九节点写出问题、假设、分工、评测门槛、MVP 行为与结果指标，并为不达标设置修复、回退或停止。
  4. 保持不变任何 AI 产品都要从可验证问题开始，以真实用户与商业结果收口，中间保留质量、风险和成本门槛。

需要提示时展开
  • 先验证失败原因，不要把“需要提醒”直接当成 AI 问题。
  • 评测既看计划内容，也看用户是否执行和恢复。
  • 结果不能只写生成次数，要包含学习行为和单位成本。

决策地图已记录。检查是否从问题开始、由结果收口。

先确认半途而废是否来自目标过大、计划不适配还是缺少反馈；假设是个性化拆解和基于完成证据的调整能提高一周执行率。AI 用于理解目标与生成候选计划，程序负责日历、完成状态和提醒。用固定目标与边界样本评测计划可执行性，记录过载、虚构资源等 Badcase；高风险健康建议拒答，监控单周活跃用户成本。MVP 只做目标收集、7 日计划、每日完成与一次调整，结果看首周完成率、次周留存、用户有效反馈与单位成本。

产品里有自由文本，就应该把整条流程都交给 AI 吗？

AI 必要性判断发生在目标之后、方案之前。关键不是“能不能用 AI”，而是哪一项子任务确实需要非结构化语言理解、开放式判断或个性化生成，并能比规则、搜索、表单或人工基线创造足够价值。

0 / 2 步
白话解释

它像决定是否雇翻译：遇到多语言自由表达时可能值得；只是把固定数字相加，就不该让翻译来算账。一个产品可以只在某一段用 AI。

它不等于什么

AI 必要性不等于模型能力展示，也不等于所有不确定问题都交给模型。固定公式、明确条件、权限和状态应优先使用确定性程序；高风险结论还需要证据和人工边界。

语义输入是否开放且难以穷举

自由表达、上下文含义、个性化内容可能需要模型。

基线规则、搜索、表单或人工是否足够

先比较更稳定、更便宜、更可解释的路径。

价值AI 改善是否影响核心结果

不是“更酷”，而是更相关、更快、更可扩展或体验更好。

边界哪些决定仍必须确定性控制

金额、计数、权限、状态、校验与高风险放行。

整条链都用 AI自由文本出现 → 模型理解 / 计算 / 审批 / 写状态

把概率性候选扩展到必须精确的控制，既难验收，也无法解释错误和恢复。

按子任务组合AI 理解与生成候选 → 程序计算 / 权限 / 写入 → 人工处理高风险

只在非 AI 基线不足且价值明确的环节引入模型。

完整示范：面试教练哪里真的需要 AI必要性落到子任务

任务：理解用户岗位和回答、生成相关追问、计算固定权重总分、限制追问次数并生成证据反馈。

  1. 已知事实回答语义和追问表达开放；固定权重、题数、权限和引用存在性都有确定规则。
  2. 第一个错误节点若因为追问需要模型，就把计分和次数也交给模型，会让硬规则随语言输出漂移。
  3. 正确动作AI 理解回答并生成候选追问与反馈；程序控制计数、公式、状态和证据核对；必要时人工处理争议。
  4. 保持不变AI 必要性按子任务判断；每一项引入都要有非 AI 基线、价值假设和控制边界。
理解检查：投诉与赔付怎样组合

系统要理解投诉自由文本并生成个性化说明，同时按固定公式计算赔付并限制审批权限。哪种分工正确？

带着资料做一次：合同条款风险提示

把上传合同、识别非标准条款、查询固定黑名单、计算金额阈值、给风险解释、决定是否允许签署分给 AI、程序和法务人工，并说明 AI 比非 AI 基线多创造什么价值。

需要提示时展开
  • 语义差异识别和解释可以由模型提出候选。
  • 固定名单、金额与签署权限不能由模型最终决定。
  • 高风险法律结论需要来源、限制和人工复核。

必要性方案已记录。检查是否按子任务比较过非 AI 基线。

页面与解析程序负责上传和固定字段；程序查黑名单、金额阈值、版本和权限。模型可识别措辞不同但语义相近的候选风险，并基于可核对条款生成解释，价值假设是提高非标准风险召回与审核效率。模型不得决定合同可签；高风险、证据冲突或未覆盖条款交法务。用固定合同集比较规则基线与组合方案的召回、误报、审核时长和严重漏检。

修掉一个 Badcase 后，为什么仍不能马上上线？

错误样本（Badcase）只是起点。团队要先归因，再修复并回归：重跑原错误样本证明问题消失，同时重跑原正常和边界用例证明没有退化；最后结合严重度、发生范围、可控性与单次会话成本决定人工接管、暂停上线或受控放量。

0 / 2 步
白话解释

它像修水管：漏点补好后，还要重新通水看原位置是否不漏、其他接口有没有被压坏；若主干仍反复爆裂，就不能只拿桶接住某一户。

它不等于什么

“再评测一次”不等于回归，“人工处理当前请求”不等于系统风险已控制，“减少 Token”也不等于可以删除下一轮仍需要的用户背景、证据和进度。

保护当前用户、保留现场；不因此宣称系统整体已修复。

证据门槛block → root cause → fix → same-set regression → risk/cost gate

完整示范：反馈编造“留存提升 25%”修复动作不是放行证据

来源：用户只说“效果很好”，模型却生成具体指标。团队在 Prompt 加了“不得编造”后单次输出正常。

  1. 已知事实原输出无来源支撑，属于高严重度证据错误；一次修后成功不能证明稳定。
  2. 第一个错误节点若直接放量，既不知道原 Badcase 是否在更多措辞上复现，也不知道修改是否让正常反馈退化。
  3. 正确动作程序核对引用并阻断；归因与修复后重跑原 Badcase、同类边界和正常用例；重复高严重度错误则暂停上线。
  4. 保持不变任何修复都要有同用例回归；人工接管保护个案，稳定门槛决定系统放量；降本后同样要回归核心质量。

留下一个理解或疑问

记录“个案人工介入”和“系统暂停上线”之间最重要的触发差异。

为什么 MVP 不是“能做多少做多少”，而是主动写下不做什么？

最小可行产品（Minimum Viable Product，MVP）用最小完整体验验证一个核心假设。范围冻结同时包含必须做、明确延后、成功指标和停止条件；没有这些边界，“以后可能需要”的功能会不断挤占本轮验证。

0 / 2 步
白话解释

它像做一道能判断味道的试菜：必须有完整的一口，但不必先装修整家餐厅。语音、支付和后台可能有价值，却不一定是这次证明用户愿意吃的必要条件。

它不等于什么

MVP 不是功能最少的残缺 Demo，也不是所有部门各塞一个需求。只实现输入却不给结果，或只做模型演示却无法让用户完成核心任务，都不是可行闭环。

核心假设这轮最需要验证什么

写成用户行为与价值结果，不写“完成某项技术”。

必须做完成端到端验证所需能力

输入、核心处理、结果与必要的安全控制缺一不可。

明确延后有价值但不影响当前假设

写下语音、支付、后台、复杂知识或自动化等边界。

指标与停止条件怎样知道继续、修改或停止

核心完成率、质量门槛、风险、成本和真实反馈。

功能投票式 MVP核心链 + 语音 + RAG + 支付 + 后台

七天被基础设施和未来需求拆散，最后没有任何一个用户完成可验证闭环。

假设驱动范围hypothesis → minimum complete journey → explicit later → metrics

每个首版能力都能说明它怎样帮助验证核心假设；其他需求被有意识延后。

完整示范：七天 AI 面试教练冻结一轮完整价值

核心假设：系统读取目标岗位与背景后，能生成与经历相关的问题，按回答决定追问或切题，并基于真实原话给出有帮助的反馈。

  1. 已知事实团队只有 7 天；语音、简历知识库、账号支付和管理后台都不是完成首轮文字练习的必要条件。
  2. 第一个错误节点若把“未来商业化需要”当成首版理由，支付和后台会挤占问题—回答—反馈闭环。
  3. 正确动作保留岗位/背景、3 道核心题与必要追问、证据反馈报告；明确延后四类需求，并定义完成率、证据正确性和用户价值反馈。
  4. 保持不变范围由当前假设和时间约束决定；核心旅程必须完整，未来能力必须可被明确推迟。
