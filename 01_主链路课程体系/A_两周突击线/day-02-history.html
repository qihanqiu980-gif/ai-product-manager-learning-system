先在脑中搭起一条链：一个需求怎样变成可解释的技术决定。

方案选型不是挑一张技术菜单，而是把产品事实逐层翻译成实现职责。先确认输入、输出、变化性、准确性、知识和执行要求，再比较普通页面与规则程序、直接提示模型、检索增强、微调或智能体；最终选择最低复杂度的组合，并把条件、取舍和失效信号写进决策记录。

先看需求，再看名词

先问任务是否需要语义理解、内容生成、外部知识或动态执行，再谈具体方案。

用错误路径建立边界

重点识别“AI 产品必须上模型”“效果差就微调”“自动化就是 Agent”等捷径。

带着资料做新场景

练习允许看提示和示例，目标是写出有依据、能落地、未来能重评的组合。

用户问题、输入输出、硬约束和必须验证的假设。

→

技术先行“做 AI” → 大模型 + RAG + Agent → 再找使用理由

复杂度已经发生，但每一层是否解决真实问题、怎样验收和何时退出都说不清。

需求先行facts → task → minimum paths → constraints → decision → review trigger

每个技术只承担它擅长的职责；没有当前证据支持的复杂度暂缓。

为什么“这是 AI 项目”还不足以开始选模型？

方案选型（Solution Selection）先比较不同实现路径，模型选择只是其中更靠后的一步。若目标可由固定表单、查询和规则稳定完成，普通程序可能比大模型更合适。

0 / 2 步
白话解释

它像决定怎么过河：先看距离、水流、人数和预算，再比较走桥、坐船还是游泳；不是先买最贵的船，再要求所有人都用它。

它不等于什么

方案选型不等于“从几个大模型中挑一个”，也不等于把所有 AI 技术都列进架构。先判断是否需要 AI、需要哪种能力，再决定是否进入具体模型比较。

输入与输出系统实际看见什么、必须交付什么

自由文本还是固定字段；生成内容还是查询与计算结果。

变化与不确定性规则能否预先写清

同一事实是否只有一个合法结果，还是需要理解语义和组织表达。

知识与执行要不要查外部资料、调用工具

资料是否频繁变化；动作是否跨系统并依赖中间结果。

验收与约束哪些条件绝不能出错

准确性、权限、时延、成本、隐私以及首版验证范围。

诱人的捷径AI 项目 → 先选最强模型

跳过了非 AI、规则程序和组合方案，无法解释为什么需要模型，也容易把硬规则交给概率输出。

正确顺序需求事实 → 实现路径 → 职责分工 → 具体模型

只有确定某个环节确实需要语言模型后，才比较质量、速度、成本、上下文容量和任务适配。

完整示范：AI 面试教练首版先冻结要验证的能力

需求：根据目标岗位和当前回答生成问题与必要追问，反馈引用真实原话；总分按固定权重计算，最多追问 3 次；暂不接知识库或其他业务系统。

  1. 已知事实问题与追问需要语义理解和语言生成；计分、次数、引用存在性和状态写入必须精确。
  2. 第一个错误节点若因“AI 面试教练”就整体做成复杂 Agent，会在没有多工具和动态任务拆解时提前承担额外成本。
  3. 正确动作选择 Prompt + LLM 负责生成候选，普通程序负责硬规则、状态与核对；暂缓 RAG、微调和复杂 Agent。
  4. 保持不变先用当前事实选能验证核心假设的最小组合；未来事实变化时重新评审，而不是现在预装全部复杂度。
理解检查：固定提醒任务的第一项决定

合同提醒首版只读取固定字段，并按到期日和负责人名单发送模板消息；没有自由文本理解、外部知识或动态工具选择。第一步怎么选？

带着资料做一次：发票归档助手

需求包括上传固定格式发票、识别备注中的自由文本用途、校验金额合计并按公司规则归档。请列出选型前事实，判断哪些环节需要 AI、哪些不需要，并写出首版最小组合。

需要提示时展开
  • 区分 OCR / 语义分类与确定性金额计算、权限、存储。
  • 不要因为出现一处 AI 就把整条流程交给模型。
  • 写出首版不采用的一种复杂方案及当前理由。

方案已记录。检查是否先写事实，再给路径。

先确认发票字段、备注样本、金额规则和归档权限。固定格式提取可优先用 OCR / 解析服务；自由文本用途分类可由模型提出候选；程序重新计算金额、查重、校验权限并写入归档。首版不需要复杂 Agent，因为步骤、接口和异常分支都可预定义；也不因少量分类样本直接微调，先建立 Prompt 与评测基线。

留下一个理解或疑问

记录“方案选型”和“模型选择”之间你刚刚分清的先后关系。

用了大模型后，为什么计数、金额和权限还要写进程序？

语言模型擅长理解模糊表达、提取语义和生成自然语言；确定性程序擅长让同一输入稳定得到同一结果，并负责硬约束、状态、写入和恢复。一个产品常需要两者组合，而不是二选一。

0 / 2 步
白话解释

模型像会判断语气和起草文案的同事；程序像收银机和门禁。可以让同事建议怎么说，但金额、次数和谁有权放行不能靠“尽量遵守”。

它不等于什么

确定性程序不只是一条 if/else，也包括数据库查询、公式、结构校验、权限、状态机和审计日志。模型输出结构正确，也不自动获得业务执行权。

Prompt + LLM理解与生成候选

看目标岗位、背景和回答，生成问题、追问与反馈草稿；不得独自决定计分、次数和正式状态。

确定性程序校验、计算与写入

控制题数、追问上限、固定权重、引用存在、权限、状态和异常恢复。

普通界面 / 流程收集、展示与确认

用表单收集确定字段，用确认步骤降低误操作；无需把每个交互都做成生成式对话。

全交给 Prompt模型生成 → 模型自查 → 直接写入

同一个概率性执行者既产生候选又批准自己，硬规则可能在边界输入上漂移。

组合分工模型候选 → 程序校验 / 计算 / 权限 → 合法写入或拒绝

语言能力被保留，必须准确的控制由可测试、可回放的程序承担。

完整示范：追问与总分怎么分工语义判断不接管硬规则

当前：用户回答只有结果，没有行动与验证；本题已追问 3 次，固定上限也是 3 次。

  1. 已知事实模型能识别证据缺口并提出追问候选；程序持有当前计数和正式上限。
  2. 第一个错误节点如果让模型同时决定“是否还能追问”，它可能因语义缺口而越过次数上限。
  3. 正确动作模型返回缺口与候选问题；程序读取计数后拒绝继续追问，转入有限报告并记录限制。
  4. 保持不变模型负责概率性语义候选，程序负责计数、公式、权限、状态和最终放行。
理解检查：退款助手怎样分工

助手要理解用户自由文本并起草回复，但退款金额公式、审批权限和每日上限必须完全准确。哪条链正确？

带着资料做一次：差旅报销助手

把“理解票据说明、判断缺什么材料、起草补充通知、计算可报金额、检查预算与审批人、写入报销状态”分给模型、普通程序或人工，并说明最终放行点。

需要提示时展开
  • 语言理解和通知草稿可由模型提出候选。
  • 金额、预算、权限、状态写入不能由候选文本决定。
  • 高风险或规则冲突时保留人工路径。

职责方案已记录。检查每项硬规则是否有明确控制者。

模型读取说明和票据文本，候选输出费用类别、缺失材料与通知草稿；程序解析结构、按政策表计算金额、检查预算 / 重复票据 / 审批权限并控制状态迁移；规则冲突、高额或证据不足转人工。只有程序校验通过或人工批准后才能写入 approved，模型不得直接修改金额和状态。

留下一个理解或疑问

记录“模型能提出什么”和“程序必须决定什么”之间最重要的边界。

模型回答不好时，什么时候该查资料，什么时候才该调整模型参数？

检索增强生成（Retrieval-Augmented Generation，RAG）解决“回答时缺少外部、私有或持续更新的知识”；微调（Fine-tuning）是在已有模型上用高质量训练样本调整参数，解决经过 Prompt 与评测后仍稳定重复的行为或能力缺口。两者不是效果差时的通用升级按钮。

0 / 2 步
白话解释

RAG 像让同事先翻最新手册再回答；微调像用大量一致范例长期训练他的做事习惯。一个补当前资料，一个改变较稳定的行为倾向。

它不等于什么

RAG 不是知识库本身，也不会自动保证资料正确、检索充分或引用忠实；微调不等于从零自建模型，也不适合每天变化的事实。更大的模型同样不能凭空知道私有或最新数据。

先做 Prompt + 评测任务和边界还没稳定

先建立基线、测试集和 Badcase；不要在问题尚未定义时训练。

比较 RAG缺外部、私有、时效或引用知识

运行时检索权威来源，把片段与问题放入 Context，再校验引用。

比较 Fine-tuning稳定行为缺口 + 高质量样本

Prompt 优化后同类能力仍重复失败，目标一致样本足够且收益能覆盖训练维护。

用户问题→检索权威知识→相关片段进入 Context→LLM 理解并生成→程序核对引用
看到 Badcase 就选技术回答错 → 上 RAG / 微调 / 换大模型

没有区分是缺知识、检索失败、Prompt 不清、稳定能力缺口，还是业务规则与数据本身有问题。

先归因再重评复现错误 → 分类根因 → 建基线 → 比较对应路径

知识根因指向检索评审；稳定行为根因和训练数据条件才指向微调评审。

完整示范：为什么当前面试教练不需要 RAG 或微调缺少启用条件

当前：首版只根据用户目标岗位、背景和本次回答生成问题与反馈；不要求读取最新 JD 或企业题库，Prompt 基线仍可继续优化，也没有成规模高质量标注样本。

  1. 已知事实输入已经包含本次生成所需事实；没有外部知识和时效引用需求，也未证明稳定能力缺口。
  2. 第一个错误节点若把“可能答不好”直接等同于需要 RAG 或微调，会跳过基线评测与根因分析。
  3. 正确动作先采用 Prompt + LLM 和固定评测集；等出现知识需求或稳定行为缺口及数据条件，再分别重评 RAG 或微调。
  4. 保持不变技术重评必须由对应事实触发：知识与来源变化不等于行为缺口，行为缺口也不等于需要外部知识。
理解检查：每天更新的制度问答

政策助手必须依据每天变化的内部制度回答，并展示可核对的最新条款。当前最直接应重评哪条路径？

带着资料做一次：员工福利问答助手

团队同时遇到两个问题：回答经常引用旧版福利政策；在资料正确时，模型仍长期不能稳定输出统一的三段式答复。请分别归因，并写出 RAG、Prompt 优化、微调的评审顺序与门槛。

需要提示时展开
  • 旧政策是知识时效问题，先看来源、检索和版本。
  • 输出结构问题先用 Prompt 与回归集证明是否稳定重复。
  • 微调还需要足够、高质量、目标一致的训练样本和收益判断。

重评方案已记录。检查知识问题与行为问题是否分开。

A 先核对权威政策库、版本字段、检索召回和引用，重评 RAG 并禁止旧版片段放行。B 先固定输入与三段式标准，用 Prompt 和回归集验证；只有优化后同类结构缺口仍稳定重复，并有足够一致的高质量示例、可接受训练和维护成本时，才比较微调。两条路径分别设知识正确率 / 引用一致性与格式稳定率，不用一次成功替代回归。

留下一个理解或疑问

记录 RAG 与微调最容易混淆的一条边界。

系统会自动调用接口，为什么仍不一定需要智能体？

普通确定性工作流把步骤、顺序、接口和异常分支预先写清；智能体（Agent）更适合目标明确但执行路径需要由模型动态拆解、选择工具、读取中间结果并调整下一步的任务。Web 页面、代码复杂或“能自动做事”都不是直接触发器。

0 / 2 步
白话解释

固定工作流像地铁：路线、站点和故障处理提前定义。Agent 更像有任务目标的外勤同事：要看现场变化决定先去哪、用什么工具、失败后怎么换路。

它不等于什么

有聊天框、有 API、有多段代码或自动排期都不等于 Agent。若输入、步骤、接口、分支和恢复能完整预定义，普通程序往往更可靠。

固定工作流程序提前知道路线

固定顺序、固定接口、预定义分支、确定状态；适合高可控、可测试流程。

Agent / 多步编排运行中决定路线

理解目标、拆分任务、选择多个工具、按中间结果改计划、维护进度并处理失败。

动态拆解

同一目标因上下文不同需要不同步骤。

多工具选择

运行时决定查哪个系统、调用什么动作。

中间结果决策

接口返回会改变下一步，而非只走预定义成功 / 失败。

跨步骤状态

保存进度、权限、补偿与受控重试。

误判 AgentWeb + API + 自动执行 → Agent

工程形态和代码量不能说明系统是否需要自主规划；固定接口自动调用仍可由普通程序完成。

先看执行自由度动态目标分解 + 工具选择 + 结果驱动分支 + 状态 → 重评

满足信号也只是重新比较 Agent 与确定性多步工作流，不是自动采用。

完整示范：固定日程与动态排期自动化不等于 Agent

场景 A：每天固定 10 点调用同一个接口创建日程。场景 B：理解自然语言偏好，查询双方日历，冲突时改选时段，创建后发提醒，接口失败时重试并保存进度。

  1. 已知事实A 的输入、时间、接口和结果分支固定；B 需要理解约束、多工具、中间结果决策与跨步骤状态。
  2. 第一个错误节点若只因“两者都自动创建日程”就都做成 Agent，会忽略执行路径是否能预先写死。
  3. 正确动作A 使用普通定时程序；B 重新比较确定性编排与 Agent，并把权限、状态、重试和补偿放在程序控制面。

已经决定用什么了，为什么还要写“不选什么”和“何时重评”？

架构决策记录（Architecture Decision Record，ADR）保存某个时间点的决策逻辑：当时面对什么背景，选择什么，比较过什么，依据和代价是什么，以及哪些事实变化会让旧决定失效。它不是技术方案简介，也不是永远不变的承诺。

0 / 2 步
白话解释

它像给未来团队留一张“为什么这样走”的路条。只写目的地不够，还要写当时封了哪些路、为何没走，以及什么情况下应该重新看地图。

它不等于什么

ADR 不是会议纪要、技术百科或最终架构图。触发器也不是“出现任何 Badcase 就换技术”，而是让团队按根因重新比较，而非自动切换。

1背景与约束

要解决什么、当时有哪些事实和边界。

2最终选择

采用哪些路径，各自承担什么职责。

3替代方案

认真比较过哪些可行路径。

4依据与取舍

为何当前组合更匹配，接受了什么代价。

5后果与风险

新能力、限制、维护成本和待验证项。

6重评触发器

什么可观察事实变化会启动重新比较。
