先在脑中搭起一条链：页面动作怎样变成可信的业务结果。

把 Web 产品想成一家办事大厅：Page 是窗口，Browser 是用户手里的表格，Server Proxy 是核验与流转中心，API Contract 是双方共同签字的办事规则，Session 是业务档案。模型以后可以提供候选内容，但不能替代这套确定性骨架。

先问“事实在哪里”

看到页面跳转、按钮禁用或 200 响应，先追问服务端保存的业务事实是否真的改变。

再问“谁有权决定”

Browser、Server、Model 和 Data 各自拥有不同输入、输出、秘密与写入权。

最后问“失败后去哪”

任何主链都要同时写出重复、超时、结构错误和刷新恢复后的合法下一步。

常见但危险的理解页面跳转成功 = 业务已经成功

它把可见界面、一次请求和持久业务事实混成了同一件事。

可验证的判断链事实 → Contract → Guard → State → Page

先由服务端确认事实和合法状态，再让页面展示对应结果；失败时仍能从同一档案恢复。

页面 URL 对了，为什么仍不能直接展示结果？

Page Flow 不是三张页面截图，而是“每个页面允许展示哪一种服务端事实”的协议。URL 只表达用户想去哪里，session 才回答他现在能去哪里。

0 / 2 步
白话解释

路由像办事大厅的门牌。你站到“领取结果”窗口，不代表档案已经审批完成；窗口仍要查档案，再决定给结果、带你回补材料，还是显示可恢复错误。

它不等于什么

/result/s-42 不等于 session.state=completed。前进、后退、刷新和手输 URL 都不能反向改写业务状态。

错误方案if (location.includes("result")) renderReport()

只信任地址，任何人都可能绕过 Guard 看到过期、空白或不属于自己的结果。

正确方案GET session → verify state → render or redirect

页面先读取服务端档案；只有状态、权限和资源身份都合法时才展示结果。

现象：用户把旧书签 /result/s-42 粘贴到新设备，但该 session 其实仍在 interviewing。

  1. 已知事实URL 请求结果页；服务端 session 尚未完成。

  4. 保持不变换成理赔、报销或签约，地址都只能投影服务端事实。

白话解释

Browser 像大厅里的公开表格；Server 像有权限的柜台；Model 像受邀提供建议的顾问。公开表格不能保管保险柜钥匙，顾问也不能自己改档案。

它不等于什么

HTTPS 只保护传输，不会把 Browser 变成秘密环境；模型响应结构正确，也不会让 Model 获得写入权。

错误方案Browser stores Key → Model writes next_state

秘密和业务决策都离开了可信控制面。

正确方案Browser → Server Guard → Mock / Model candidate → Validator → State

服务端守秘密、执行确定性规则，再返回可展示结果。

完整示范：前端环境变量里的 Key先止损，再重建边界

现象：团队把 MODEL_API_KEY 写进前端构建变量，并说“用户看不到源代码”。

  1. 已知事实前端资源会下载到设备，网络请求也可被检查。
  2. 第一个错误节点秘密已经跨进公开的 Browser 边界。
  3. 正确动作停止调用并轮换 Key；Browser 只发业务字段，Server 从环境变量读取 Key。
  4. 保持不变任何供应商、任何客户端框架都不能改变秘密只留服务端的规则。

接口返回 200，为什么仍可能破坏产品合同？

API Contract 不只规定“请求能不能通”，还规定字段语义、允许状态、错误结构、幂等身份和恢复动作。HTTP 200 只是运输状态，不是业务正确证明。

0 / 2 步
白话解释

Contract 像柜台的办事清单：交什么材料、成功后拿到什么、材料不全会收到哪个错误、能否原地补交，都要提前约定。

它不等于什么

它不是一份只列 URL 的接口目录，也不是“所有异常都返回 200 + message”。Schema 形状正确仍需业务语义校验。

Input允许字段与约束

业务字段、资源身份、版本、request_id。

Success成功语义

返回什么事实，是否真的发生写入。

Error稳定错误结构

code、message、retryable、recovery_action。

State合法状态变化

当前状态、Guard、next_state、next_route。

Idempotency重复请求语义

同一 request_id 返回同一写入结果。

错误方案200 { "ok": true, "message": "failed" }

客户端无法区分成功事实、可重试故障和需要用户补资料的业务阻断。

正确方案409 { code, retryable, recovery_action, current_state }

传输状态、业务错误和恢复动作保持一致且可编程。

完整示范：回答提交后题目没推进核对成功语义

现象：POST /answers 返回 200 和新题，但服务端没有保存原回答，也没有返回版本和 request_id。

  1. 已知事实传输成功；持久写入与幂等证据缺失。
  2. 第一个错误节点接口把“生成了下一题”误写成“回答提交成功”。
  3. 正确动作先原子保存回答并绑定 request_id，再由 Guard 推进 session，返回版本化 session 与 next_route。
  4. 保持不变所有写接口都要定义“成功到底写成了什么”，不能只看状态码。

按钮禁用过了，为什么重复提交仍可能写两次？

按钮禁用只管理当前页面的 Request State。刷新、双设备、网络重放和响应晚到都可能绕过它，所以 Session、Page、Request、Recovery 必须分层，服务端还要用 request_id 保证幂等。

0 / 2 步
Session State业务事实

服务端保存流程走到哪里、已经写入什么。

Page State可见投影

页面和控件根据 session 显示，不反向造事实。

Request State单次请求

idle、submitting、success、error 与晚到响应。

Recovery State失败出口

保留什么、能否重试、从哪个事实恢复。

白话解释

禁用按钮像提醒眼前这个人“别再按”；request_id 像柜台受理号，保证同一件业务即使被重放，也只记一次账。

它不等于什么

loading 不是幂等，重新生成 UUID 也不是安全重试。恢复时必须保留原 session、原输入和同一个业务请求身份。

错误方案click → disable → retry with new UUID

页面重开或网络代理重放时仍会产生第二次写入。

正确方案stable request_id → atomic write → replay same result

服务端把请求身份和写入结果绑定，同 ID 重试返回同一结果。

完整示范：提交超时后用户刷新先查事实，再决定重试

现象：页面提交回答后超时，用户刷新；原请求可能已经写入，只是响应没回来。

  1. 已知事实客户端不知道结果；服务端可能已写入。
  2. 第一个错误节点若创建新 request_id 重新提交，就可能写两次。
  3. 正确动作保留原 request_id 和草稿，先 GET session 或用同 ID 重试；服务端重放原结果。
  4. 保持不变支付、工单、回答和审批写入都需要稳定身份与原子幂等。
