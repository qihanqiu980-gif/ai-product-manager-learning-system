写了“正常案例、边界案例”，为什么模型还是学不会？

少样本提示（Few-shot Prompting）不是给示例起名字，而是把某类具体输入与合格输出完整摆在模型面前，让它在本次上下文里模仿行为。

0 / 2 步
白话解释

它像带新人看两次真实接待：不能只说“这是好案例”，而要让他看见顾客说了什么、店员怎么判断、最后具体说了哪句话。

它不等于什么

“用户回答具体”“模型不要幻觉”只是标签和原则；没有真实 Input 与 Expected Output，模型不知道该抓哪条证据、该输出什么动作。Few-shot 也不会永久修改模型参数。

Input模型当时看见的具体事实

当前问题、用户原话和必要上下文，不能只写“回答具体”。

Expected Output可以直接模仿的合格结果

明确 action、下一句话、结构和不允许添加的事实。

Why It Matters这个示例守哪条边界

说明它纠正哪个 Badcase，以及与其他示例的差异。

空壳示例Input: 用户回答；Output: 根据证据继续

没有可观察证据，也没有一句可模仿输出，模型只能靠自己的宽泛理解补全。

完整映射具体问题 + 用户原话 → action + 一句下一问 + 理由

输入和输出一一对应，模型能看见规则在具体边界上怎样执行。

完整示范：回答只有“我看了数据”证据不足分支

当前问题：“请介绍一次你提升 DAU 的项目。”回答：“我查看了数据，提高了 DAU。”

  1. 已知事实回答给出结果结论，但没有指标、分析过程、具体动作或验证。
  2. 第一个错误节点若示例只标“空泛回答”，模型仍不知道下一句要追哪类证据。
  3. 正确动作Expected Output 设为 ask_follow_up，并追问采用什么分析方式、发现什么问题、做了什么。
  4. 保持不变任何 Few-shot 示例都必须让具体输入与可执行输出形成可模仿映射。

为什么一正一反两个示例，常比两个成功案例更有用？

示例的价值不在数量，而在是否覆盖最容易走错的决策边界。两个相似成功案例只重复同一模式；对照示例让模型看见“什么变化会触发不同动作”。

0 / 2 步
白话解释

教人分红绿灯，最好同时展示“红灯停、绿灯行”，而不是给两张不同路口的绿灯照片。差异明确的例子更能教会分界。

它不等于什么

示例越多不一定越稳：重复样本会增加 Token 成本、挤占上下文，还可能让模型只记表面措辞。示例效果也不能靠一次顺利输出下结论。

证据不足ask_follow_up

回答只有结论，没有行动、验证和结果；下一句只追当前最高优先缺口。

证据充分ask_new_question

背景、行动、验证和可核验结果已经清楚；进入尚未覆盖的新能力点。

低信息增益成功案例 A + 成功案例 B

两份示例都走相同动作，模型仍不知道遇到证据不足时应停下还是切题。

高信息增益boundary A → action X; boundary B → action Y

只改变关键条件，展示动作怎样随证据边界变化。

完整示范：同一面试问题的两种回答分支由证据变化触发

问题：“请介绍一次留存优化。”回答 A 只有“优化后留存提升”；回答 B 包含三步引导、A/B 测试以及 7 日留存从 18% 到 25%。

  1. 已知事实A 缺少行动与验证；B 有问题、行动、实验和量化结果。
  2. 第一个错误节点若两个示例都用成功叙述，模型看不到何时需要继续追问。
  3. 正确动作A → ask_follow_up；B → ask_new_question，并用固定测试集核对分支稳定性。
  4. 保持不变选例先覆盖关键决策边界，再用固定用例回归，不按示例数量制造信心。

模型已经返回 JSON，为什么仍需要一份 Schema？

JSON Schema 是机器可以执行的结构合同：根结果是什么类型、允许哪些字段、哪些必填、每个值是什么类型和范围、数组里的每一项又受什么限制。

0 / 2 步
白话解释

JSON 像填好的表格；Schema 像表格模板和验收规则。能打开表格不代表列名正确、必填项齐全、选项合法，也不代表没有偷偷多出一列。

它不等于什么

Schema 不是这一次的具体输出，也不是 Prompt 的自然语言重复。required 声明每次必须有哪些字段；properties 定义字段契约；additionalProperties: false 拒绝未声明字段。

Root Typetype: object

先声明整个结果是一份对象，而不是数组或自由文本。

Properties每个字段各有规则

string 用长度；单值分支用 enum；array 的元素约束放进 items。

Required必填字段名数组

列出 next_action、question、summary、quotes、risk_flags。

Closed ObjectadditionalProperties: false

禁止模型把 extra_note 等未声明字段混入下游。

数组外层type / minItems / maxItems / uniqueItems

约束整个容器有多少项、能否重复。

items 元素层type / enum / maxLength

约束数组里的每一项是什么、允许哪些值、多长。

层级混乱risk_flags: enum + maxLength

把数组本身和数组元素混在一起，规则看似齐全但 validator 无法按预期执行。

层级清楚array → items { string + enum }; uniqueItems/maxItems outside

容器规则放外层，元素规则放 items，根级 required 与关闭额外字段独立存在。

完整示范：文本能解析，但违反四条契约Schema 负责确定性拒绝

候选：next_action="continue"、evidence_quotes 是字符串、缺少 risk_flags，并多出 extra_note。

  1. 已知事实它是合法 JSON，所以解析成功；但枚举、类型、必填和额外字段均违规。
  2. 第一个错误节点若把“能解析”当“符合契约”，非法结构就会进入业务流程。
  3. 正确动作validator 用 enum / type / required / additionalProperties 分别报错并阻断。
  4. 保持不变先设计清楚根、字段、数组和元素层级，再让机器按同一契约验收每次输出。

留下一个理解或疑问

记录 Schema 中最容易写错的一个层级关系。

Prompt 已写“严格按格式”，为什么程序还要验三次？

Prompt 是生成前的概率性引导；解析器、Schema validator 和业务校验是在输出后的确定性验收。三层回答不同问题，任何一层通过都不能代替另外两层。

0 / 2 步
白话解释

它像机场安检：登机牌能不能读、证件字段是否齐全、证件是否属于本人是三件不同的事。前一关通过，不代表后一关自动通过。

它不等于什么

JSON.parse 成功只说明语法成立；Schema 通过只说明结构合约满足；它们都不能证明引用来自原文、结论真实或业务动作被授权。

Layer 1JSON 解析

文本是否是合法 JSON；拒绝代码围栏、解释文字、缺逗号或坏引号。

Layer 2Schema 校验

字段、类型、必填、枚举、长度、数组和额外字段是否合约。

Layer 3业务校验

引用是否来自输入，action 与证据是否一致，权限与风险规则是否允许。

Release三层通过才放行

任何失败都阻断候选；不得用模型自评替代确定性结果。

错误放行valid JSON = safe business result

结构漂亮的幻觉引用、越权动作或错误结论仍会进入下游。

正确放行parse pass ∧ schema pass ∧ business pass

每层记录自己的通过/拒绝原因，全部满足才使用结果。

完整示范：Schema 通过，但引用不存在结构正确不等于事实正确

候选：五个字段、类型和枚举全都合法；evidence_quotes 却包含“7 日留存提升 25%”，用户原回答没有这句话。

  1. 已知事实JSON 可解析，Schema 通过；引用与来源文本不一致。
  2. 第一个错误节点若 Schema 通过就放行，会把结构化幻觉包装成可信证据。
  3. 正确动作业务校验比对原文并拒绝，记录 quote_not_found，不让候选进入面试反馈。
  4. 保持不变结构校验保证“长得合约”，业务校验才判断“内容有资格被使用”。

留下一个理解或疑问

记录解析、Schema 与业务校验中最容易互相替代的一对。

校验失败后，为什么不能让模型一直重写到成功？

有限重试只修复明确、可纠正的失败：先阻断违规候选，把字段路径、期望规则和实际错误反馈给模型，要求只返回修正 JSON；每次仍按同一契约重验，并在固定次数后停止。

0 / 2 步
白话解释

它像退回一份表格：不是说“重填一下”，而是指出“第 3 行日期格式错误、缺少签名”，让对方只改这些；退回次数达到上限就转人工，不把窗口堵死。

它不等于什么

重试不是重新自由发挥整个任务，也不是保证最终成功。若根因是 Schema、Prompt、上下文或模型能力不匹配，重复生成会增加成本和延迟，甚至形成循环和故障放大。

1Block

违规输出不得进入业务流程，保留原始候选。

→
2Explain Error

记录字段路径、期望约束和实际错误。

→
3Repair Only

要求只修违规项，只返回 JSON，不新增事实。

→
4Revalidate

重新解析、Schema 与业务校验，不因重试而免检。

→
5Limit & Fallback

最多 2 次；仍失败则停止调用并转人工或安全兜底。

盲目重试invalid → “please try again” → repeat forever

错误信息不具体，模型可能反复犯同一错；成本、延迟和并发资源持续增长。

有限修复block → exact errors → repair only → revalidate → max 2 → fallback

失败路径可预测、可观察、可停止，旧候选和每次错误都可回放。
